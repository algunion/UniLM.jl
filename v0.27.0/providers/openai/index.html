Language models · OpenAI

OpenAI

OpenAI makes the GPT models. OPENAIServiceEndpoint speaks two of OpenAI's APIs for them: Chat Completions, where every request is a Chat sent by chatrequest! or tool_loop!, and Responses, where every request is a Respond sent by respond or tool_loop. The same endpoint reaches OpenAI's embeddings, image, audio and platform APIs, and OpenAI's Decisions API, which ask speaks, has an entry of its own: OpenAI Decisions API. No verb of a capability the table below lists as not available sends a request through this endpoint. Of the two APIs, UniLM sends no Responses prompt template and no access_programs, does not use the Responses API's WebSocket mode, and does not read back the completions a Chat Completions request stores with store=true.

Setup

Set your API key in the environment Julia starts from:

export OPENAI_API_KEY="sk-..."

UniLM reads the variable each time a request is sent: a chatrequest! or respond without it returns a call-error result, an LLMCallError or a ResponseCallError, whose cause is the KeyError naming it. OPENAIServiceEndpoint is the default service of Chat, Respond and Embeddings; the examples on these pages pass it as service=OPENAIServiceEndpoint, the bare type, or leave it to the default. Requests go to https://api.openai.com — a Chat to /v1/chat/completions, a Respond to /v1/responses — with the key in an Authorization: Bearer header.

A Chat or Respond without model takes the default model named at the top of this page. A request that sets no reasoning effort runs at the model's default effort, and UniLM checks the rules of the model's row in the rule table at that effort, the row's Default effort cell. Where the row takes sampling controls or Chat Completions tools only at another effort, as the default model's row does, a request that sets them must name that effort: the check runs when the request is encoded, before anything is sent, and throws ArgumentError (Limits and refusals), while the Chat constructor accepts the request:

chat = Chat(service=OPENAIServiceEndpoint, temperature=0.2)
push!(chat, Message(Val(:system), "You are a concise assistant."))
push!(chat, Message(Val(:user), "Name a prime number."))
refusal = try UniLM.encode_request(chat.service, chat); nothing catch err; err end
refusal isa ArgumentError || error("expected the request to be refused")
print(refusal.msg)

With the effort the message names, the same request is sent as it stands:

chat = Chat(service=OPENAIServiceEndpoint, temperature=0.2, reasoning_effort="none")
push!(chat, Message(Val(:system), "You are a concise assistant."))
push!(chat, Message(Val(:user), "Name a prime number."))
print(UniLM.encode_request(chat.service, chat))

UniLM.encode_request returns the body chatrequest! sends, or throws the refusal, with no key and no request. Another model is a model away; which models UniLM holds rules and prices for is on Models.

Chat Completions or Responses

OpenAI serves the default model on both APIs, Chat Completions and Responses (GPT-6 Sol, Endpoints), and a program may use both through the same endpoint. They differ in where the conversation lives and in what a request may carry:

For tool calling, OpenAI's guide to its GPT-6 models points to the Responses API: "Use Responses for reasoning with tools" (GPT-6 guide). On Chat Completions, a model of the rule table takes function tools only at the efforts its Chat Completions tools column lists, none where the cell is "—", and the reasoning efforts the two APIs take differ per model: UniLM refuses a request that breaks either rule, and the refusal's message names the fix (Limits and refusals). The hosted tools are tools of the Responses API: Chat Completions "supports only specialized search models for web search" (web search). Audio input and spoken replies are Chat Completions features, which OpenAI's audio guide directs to "Chat Completions with an audio-capable model" (Audio in Chat Completions).

First call

On Chat Completions, a Chat starts with its system message; chatrequest! sends it and returns a typed result, and text reads the reply — or throws, on a failure:

chat = Chat(service=OPENAIServiceEndpoint)
push!(chat, Message(Val(:system), "You are a concise assistant."))
push!(chat, Message(Val(:user), "In one sentence: what is a prime number?"))
result = chatrequest!(chat)
text(result)

result.model, result.message.finish_reason

result.model is the model that served the reply, as OpenAI reports it, and the model estimated_cost prices the call at. finish_reason is OpenAI's: "stop", "length" "if the maximum number of tokens specified in the request was reached", "tool_calls", or "content_filter" (Create chat completion); a turn that carries tool calls reads "tool_calls" when OpenAI finished it with "stop".

u = result.usage
(; u.prompt_tokens, u.completion_tokens, u.reasoning_tokens, u.cached_tokens, u.service_tier,
   cost = estimated_cost(result))

prompt_tokens counts all the input, the cache reads (cached_tokens) and writes (cache_write_tokens) among it, and completion_tokens all the output, the reasoning (reasoning_tokens) included; service_tier is the tier OpenAI reports processing the call at. How these become a price is on Cost and usage, and the result types on Results.

On Responses, respond takes the input and the request's fields as keywords, and output_text reads the answer:

result = respond("In one sentence: what is a prime number?"; service=OPENAIServiceEndpoint,
                 instructions="You are a concise assistant.")
output_text(result)

u = token_usage(result)
(; result.response.model, result.response.status, u.prompt_tokens, u.completion_tokens,
   u.reasoning_tokens, cost = round(estimated_cost(result); digits=6))

A Responses result holds the response as OpenAI sent it: result.response is a ResponseObject with its id, status, model, output items, usage and the whole body as raw, and token_usage reads its usage into the same TokenUsage a Chat result carries. What else a Respond takes is on Responses & hosted tools.

Conversations

A Chat keeps the conversation: each reply is appended to it, and the next chatrequest! sends the whole conversation again.

chat = Chat(service=OPENAIServiceEndpoint)
push!(chat, Message(Val(:system), "You are a concise assistant: answer in one short sentence."))
push!(chat, Message(Val(:user), "Which planet of the solar system is the largest?"))
text(chatrequest!(chat))

push!(chat, Message(Val(:user), "And the smallest?"))
text(chatrequest!(chat))

[m.role for m in chat.messages], cumulative_cost(chat)

The messages go out in the order they were pushed, system messages where they stand, and a reply goes back as its text and tool calls; a spoken reply also goes back by its audio id (Audio replies). A Message needs a text, tool calls, a refusal, attachments or an audio reply, and its constructor throws ArgumentError for one that has none; what push! refuses is the same on every provider (Conversations with Chat).

A response is stored by OpenAI unless the request sets store=false: OpenAI keeps it "for at least 30 days" (Create a model response). The next request names it with previous_response_id and sends only the new input:

r1 = respond("Which planet of the solar system is the largest?"; service=OPENAIServiceEndpoint,
             instructions="You are a concise assistant: answer in one short sentence.")
output_text(r1)

r2 = respond("And the smallest?"; service=OPENAIServiceEndpoint, previous_response_id=r1.response.id,
             instructions="You are a concise assistant: answer in one short sentence.")
output_text(r2)

Each request names its instructions again, since "the instructions from a previous response will not be carried over to the next response" (Create a model response, instructions), and "all previous input tokens for responses in the chain are billed as input tokens" (conversation state). A Conversations API object holds a conversation instead: respond(input; conversation=id) adds the response's input and output to it, and a Respond refuses conversation together with previous_response_id (Limits and refusals); the conversation itself is made by create_conversation (Platform APIs). A request that replays the conversation's items itself, rather than chaining, sends them as its input (Input).

Streaming

With stream=true, chatrequest! returns a Task at once, and fetch gives the same typed result as an unstreamed call. The callback receives the text as it arrives, a String at a time, then the assembled Message:

chat = Chat(service=OPENAIServiceEndpoint, stream=true)
push!(chat, Message(Val(:system), "You are a concise assistant."))
push!(chat, Message(Val(:user), "List the planets of the solar system in order, one per line."))
deltas = String[]
task = chatrequest!(chat; callback=(chunk, close) -> chunk isa String && push!(deltas, chunk))
result = fetch(task)
text(result)

length(deltas), result.usage.completion_tokens, estimated_cost(result)

A Chat whose stream_options is unset asks OpenAI for the stream's usage, as stream_options = {"include_usage": true}, so a streamed turn has usage and adds its cost to cumulative_cost as an unstreamed one does. OpenAI then streams "an additional chunk" before data: [DONE], whose usage covers the whole request and whose choices is empty, and "If the stream is interrupted or cancelled, you may not receive the final usage chunk" (Create chat completion, stream_options and the chunk's usage):

  • End. The turn is final at [DONE], or, without one, when the HTTP body ends after the finish reason: the Message reaches the callback then.
  • Stops. close[] = true in the callback, or a cancelled CancelToken, ends the call with an LLMCallError whose cause is a UniLMCancelled — unless the finish reason had arrived: then the turn is committed, and its usage may be missing (Stopping a Stream Early). A stream stopped before its usage chunk adds nothing to cumulative_cost.
  • Tool calls. on_tool_call(tc) runs once per call whose arguments decode, when its arguments are whole: as the next call begins, or at the end of the stream (Tools on Chat Completions).
  • Spoken replies. The transcript of an audio reply reaches the callback as text, and the audio is assembled from its chunks (Audio replies).

respond streams with a do block, whose function receives the text, then the ResponseObject of a response that completed or ended incomplete; the response's usage comes with it:

deltas = String[]
task = respond("Name the four largest moons of Jupiter, one per line."; service=OPENAIServiceEndpoint) do chunk, close
    chunk isa String && push!(deltas, chunk)
end
result = fetch(task)
output_text(result)

length(deltas), token_usage(result).completion_tokens, estimated_cost(result)

A Responses stream ends at its terminal event: response.completed and response.incomplete give a ResponseSuccess, response.failed a ResponseFailure. A stop before that event ends the call with a ResponseCallError whose cause is the UniLMCancelled. The concepts every provider shares are on Streaming.

Embeddings

An Embeddings request on OPENAIServiceEndpoint goes to /v1/embeddings, on OpenAI's text-embedding-3-small unless it names a model. It holds one text or several, and embeddingrequest! fills its pre-allocated vectors in place:

emb = Embeddings(["The Pacific is the largest ocean.", "Mercury is the smallest planet."];
                 service=OPENAIServiceEndpoint, dimensions=256)
result = embeddingrequest!(emb)
length.(embedding_vectors(result)), token_usage(result).prompt_tokens, estimated_cost(result)

By default "the length of the embedding vector is 1536 for text-embedding-3-small or 3072 for text-embedding-3-large" (embeddings guide). dimensions is sent as it is: the text-embedding-3 models return a shorter vector when a request asks for one (embeddings guide), and UniLM checks only that it is positive. The buffers start at dimensions, else 1536, numbers per text, and take the length the reply has. An embedding bills its input tokens alone, at the rate of the model's row in the price table. An image or a sound clip, a title, and a task other than :none are refused before the request: the OpenAI Embeddings API takes text, and UniLM writes a task prompt only for the models it knows to read one (Limits and refusals). The concepts every provider shares are on Embeddings.

When something fails

chatrequest!, respond and embeddingrequest! return what the service or the network did as a typed result, and do not throw it (Results). A failure is an LLMFailure, ResponseFailure or EmbeddingFailure, holding OpenAI's HTTP status and, as response, the body that came with it; or an LLMCallError, ResponseCallError or EmbeddingCallError, holding the text of the exception as error and the exception as cause. A failure of a Chat or a Respond keeps the reply's x-request-id header, when one came, as request_id.

UniLM sends a request again after a transient status — 408, 429, 500, 502 to 504, 520 to 524 and 529 — as often as the call's RequestConfig allows, waiting at least as long as the reply asks, by its retry-after-ms header, else Retry-After, and then returns the last answer (Timeouts & Retries). A 429 whose error.code is credit_balance_exhausted, organization_spend_limit_exceeded, project_spend_limit_exceeded or organization_usage_limit_exceeded, or whose error.type or error.code is insufficient_quota, is returned at once: "Retrying billing, spend, or quota errors won't restore API access" (error codes). A streamed request is sent again only while none of its callbacks has run. The lifecycle calls of stored responses — get_response, delete_response, list_input_items, cancel_response, compact_response and count_input_tokens — make one attempt, which max_attempts does not change.
