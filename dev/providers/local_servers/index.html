Language models · Local models

vLLM, LM Studio & llama.cpp

vLLM, LM Studio and llama.cpp's llama-server serve open models from your own machine, or a server of yours, through an OpenAI-compatible API, and GenericOpenAIEndpoint speaks it: under the server's base URL, a Chat goes to /v1/chat/completions, an Embeddings request to /v1/embeddings, respond to /v1/responses, fim_complete to /v1/completions and transcribe to /v1/audio/transcriptions. UniLM is an OpenAI-compatible client there: it holds no rule of any server, sends every field a request sets as it is, under the name the request gives it — LM Studio's chat reference lists the cap as max_tokens (chat completions), while vLLM takes max_completion_tokens and deprecates max_tokens "in favor of the maxcompletiontokens field" (protocol) —, and refuses what Limits and refusals lists. A verb that needs a capability the table below lists as not available refuses this endpoint, and so does ask; respond, which takes responses or agentic, and transcribe, which takes transcription or audio, are sent. Local decision models have an entry of their own: Local decision models. UniLM does not use the servers' own APIs either, such as llama-server's /completion and /infill or LM Studio's REST API. The examples on this page ran on llama-server.

Setup

Start the server with the model it serves:

vllm serve Qwen/Qwen3-8B                       # vLLM, at http://localhost:8000
lms server start                               # LM Studio, at http://localhost:1234
llama-server -m model.gguf --alias d1-3b       # llama.cpp, at http://127.0.0.1:8080

vLLM's examples reach its server at http://localhost:8000/v1 (OpenAI-compatible server), LM Studio's assume "the server port is 1234" (OpenAI compatibility), and llama-server "by default listens on 127.0.0.1:8080" (server). A GenericOpenAIEndpoint takes the server's base URL and a key:

vllm = GenericOpenAIEndpoint("http://localhost:8000", "")
lmstudio = GenericOpenAIEndpoint("http://localhost:1234", "")
llama = GenericOpenAIEndpoint("http://127.0.0.1:8080", "")

The base URL is the server's root, without /v1: UniLM appends /v1/chat/completions and the other paths, and drops a trailing /. An empty key sends no Authorization header, which suits the servers as they start: "By default, LM Studio does not require authentication for API requests" (authentication), and vLLM and llama-server check a key only when started with one, --api-key (vLLM also VLLM_API_KEY). A key given, GenericOpenAIEndpoint(url, "sk-…"), goes as Authorization: Bearer; with GenericOpenAIEndpoint(url, "", "MY_SERVER_KEY") UniLM reads the key from that environment variable each time a request is built, and a request without it fails, naming the variable.

The endpoint has no default model: a Chat, Respond, Embeddings or FIM request names the model the server serves, or throws ArgumentError before anything is sent. vLLM serves a model under the name vllm serve was given, LM Studio under the identifier of a loaded model, and llama-server under its --alias, else the path given with -m: "By default, model id field is the path to model file" (server). list_models refuses this endpoint, so read the server's own /v1/models.

First call

A Chat starts with its system message; chatrequest! sends it and returns a typed result, and text reads the reply — or throws, on a failure:

llama = GenericOpenAIEndpoint("http://127.0.0.1:8080", "")
chat = Chat(service=llama, model="d1-3b")
push!(chat, Message(Val(:system), "You are a concise assistant."))
push!(chat, Message(Val(:user), "In one sentence: what is a prime number?"))
result = chatrequest!(chat)
text(result)

result.model, result.message.finish_reason

u = result.usage
(; u.prompt_tokens, u.completion_tokens, cost = estimated_cost(result))

result.model is the model the server names in its reply, and the reply's finish_reason and usage are read as the OpenAI-compatible API defines them. A model has no price row unless you add one, so estimated_cost gives 0.0 and logs one warning per model id — the first chatrequest! logs it, as it adds each call's cost to cumulative_cost. Pass estimated_cost a pricing table holding the model's row, or add the row to DEFAULT_PRICING, to price your own server's time (Cost Tracking); a result whose usage counts audio tokens is estimated at 0.0 with a warning even then, since a row holds no audio rates.

A reasoning model's reasoning comes back beside the answer — llama-server returns it "via the reasoning_content field" (server), vLLM in a reasoning field, which "used to be called reasoning_content" (reasoning outputs) — and UniLM keeps either on the message, from the reply or from a stream's deltas of that name, where reasoning_text reads it; a stream cut before its finish reason keeps none. The reasoning does not go back with the next turn. The result types are on Results.

Streaming

With stream=true, chatrequest! returns a Task at once, and fetch gives the same typed result as an unstreamed call; the callback receives the text as it arrives, then the assembled Message. A Chat on this endpoint sends no stream_options unless it sets them, so a streamed turn reports no usage, and adds 0.0 to cumulative_cost, unless the Chat sets stream_options=Dict("include_usage" => true), which llama-server honoured below:

chat = Chat(service=llama, model="d1-3b", stream=true, stream_options=Dict("include_usage" => true))
push!(chat, Message(Val(:system), "You are a concise assistant."))
push!(chat, Message(Val(:user), "List the planets of the solar system in order, one per line."))
deltas = String[]
task = chatrequest!(chat; callback=(chunk, close) -> chunk isa String && push!(deltas, chunk))
result = fetch(task)
text(result)

length(deltas), result.usage.completion_tokens

The stream is the OpenAI-compatible one: the turn is final at data: [DONE], or, without one, when the HTTP body ends after the finish reason; on_tool_call(tc) runs once per call whose arguments decode, as the next call begins or at the end of the stream; and setting close[] = true stops it (Stopping a Stream Early). The concepts every provider shares are on Streaming.

Tools

Each Tool in tools goes out as a function tool, and tool_choice, parallel_tool_calls and a tool's strict go as they are set; a Chat with tools sends parallel_tool_calls: false unless it sets another value. What the server does with them is its own: vLLM lets the model choose a call only when started with --enable-auto-tool-choice and a --tool-call-parser (tool calling), llama-server takes tools through its Jinja chat templates, which its --jinja flag turns on, "default: enabled" (server), and on it "Multiple/parallel tool calling is supported on some models but disabled by default" (function calling), and LM Studio warns that "Smaller models and models that were not trained for tool use may output improperly formatted tool calls" (tool use). tool_loop! runs the calls and sends their results back until the model answers in text:

weather = UniLM.CallableTool(
    Tool(func=FunctionSignature(name="get_weather", description="Current weather in a city",
        parameters=Dict("type" => "object", "required" => ["city"],
                        "properties" => Dict("city" => Dict("type" => "string"))))),
    (name, args) -> "18°C and sunny in $(args["city"])")
chat = Chat(service=llama, model="d1-3b", tools=[weather])
push!(chat, Message(Val(:system), "You are concise."))
push!(chat, Message(Val(:user), "What is the weather in Lyon? Use the tool, then answer in one sentence."))
loop = tool_loop!(chat; tools=[weather])
calls = [(o.tool_name, o.arguments) for o in loop.tool_calls]
loop.completed, calls, text(loop.response)

The loop every provider shares is on Tool Calling.

Structured output

A JSON Schema response_format goes out as the OpenAI-compatible API defines it, {"type": "json_schema", "json_schema": {"name": …, "schema": …}}, and UniLM.json_object() as {"type": "json_object"}; the server constrains the reply. vLLM takes a json_schema response_format (structured outputs), LM Studio a JSON schema on /v1/chat/completions (structured output), and llama-server "schema-constrained JSON" (server):

using JSON
schema = Dict("type" => "object", "additionalProperties" => false,
              "required" => ["name", "year", "city"],
              "properties" => Dict("name" => Dict("type" => "string"),
                                   "year" => Dict("type" => "integer"),
                                   "city" => Dict("type" => "string")))
chat = Chat(service=llama, model="d1-3b", response_format=UniLM.json_schema("person", "A person", schema))
push!(chat, Message(Val(:system), "You extract facts."))
push!(chat, Message(Val(:user), "Extract the person: Ada Lovelace, born 1815 in London."))
JSON.parse(text(chatrequest!(chat)))

The formats every provider shares are on Structured Output.

Embeddings, respond, FIM and transcription

These calls reach the server's other OpenAI-compatible routes; this page did not run them, so their code stands without output:

emb = Embeddings(["first text", "second text"]; service=vllm, model="BAAI/bge-m3")
embeddingrequest!(emb)                                                    # /v1/embeddings
result = respond("Name a prime number."; service=llama, model="d1-3b")   # /v1/responses
fim = fim_complete("def area(r):\n    "; suffix="\n    return a\n",       # /v1/completions
                   service=lmstudio, model="qwen2.5-coder-1.5b")
heard = transcribe("memo.wav"; service=vllm,                              # /v1/audio/transcriptions
                   model="openai/whisper-large-v3-turbo", language="en")

Embeddings

Embeddings need an embedding model: vLLM's embeddings route is "Only applicable to embedding models" (OpenAI-compatible server), and llama-server's "requires that the model uses a pooling different than type none". An item holding an image or a sound clip is refused before the request: UniLM sends these routes text only, though vLLM takes images too, "by defining a custom chat template for the server and passing a list of messages in the request" (embeddings), a request UniLM does not write. EmbeddingGemma's task prompts hold on any server (task prompts). The concepts every provider shares are on Embeddings.

respond

respond sends a Respond's fields as they are, a seed among them: vLLM's Responses API "forwards vLLM sampling parameters such as top_k, min_p, repetition_penalty, seed, stop, and ignore_eos to the engine" (OpenAI-compatible server). vLLM serves stored responses (/v1/responses/{response_id}), LM Studio takes a previous_response_id, and llama-server's route "works by converting Responses request into Chat Completions request".

FIM completion

FIM sends the suffix to /v1/completions, where vLLM's Completions API notes "suffix parameter is not supported", so a vLLM server cannot fill in the middle. The concepts every provider shares are on FIM & Prefix Completion.

Transcription

transcribe sends the file and the fields a request sets to /v1/audio/transcriptions, where vLLM's Transcriptions API is "Only applicable to Automatic Speech Recognition (ASR) models" (OpenAI-compatible server) and takes model as "required" (speech to text): the endpoint has no default model, so a call names the server's. speak and translate refuse the endpoint.

Limits and refusals

UniLM checks no limit of a server: a request longer than the model's context window, or one the model cannot serve, is the server's error (When something fails). It refuses before anything is sent what the table below lists, and the checks every Chat and Embeddings request gets, such as a temperature from 0 to 2, an n of 1 or a positive dimensions; the verbs of the capabilities the table at the top of this page lists as not available refuse the endpoint too.

When something fails

chatrequest!, respond, embeddingrequest! and fim_complete return what the server or the network did as a typed result, and do not throw it (Results). A failure holds the server's HTTP status and, as response, the body that came with it; a call error holds the text of an exception as error and the exception as cause. UniLM sends a request again after a transient status — 408, 429, 500, 502 to 504, 520 to 524 and 529 — or a failed connection, as often as the call's RequestConfig allows, and then returns the last answer (Timeouts & Retries); a streamed request is sent again only while none of its callbacks has run.
