Language models · Local models

Ollama

Ollama runs open models on your own machine, and OllamaEndpoint speaks its native API: a Chat goes to /api/chat and an Embeddings request to /api/embed, the routes that take the context window, how long a model stays loaded, thinking and truncation. respond, compact_response, fim_complete and transcribe reach Ollama's OpenAI-compatible routes instead, which carry none of the endpoint's options. No key is sent to a server of your own, and a local model costs nothing unless you give it a price. A verb that needs a capability the table below lists as not available refuses this endpoint, speak among them, though Ollama serves speech at /v1/audio/speech; respond, which takes responses or agentic, and transcribe, which takes transcription or audio, reach Ollama. Of Ollama's own API, UniLM does not wrap /api/generate, /api/version, creating, copying or pushing a model, or web search and web fetch. The decision models ask reaches through the same endpoint have an entry of their own: Local decision models.

Setup

Install Ollama and start it, the desktop app or ollama serve, then pull the models the examples run on:

ollama pull gemma4:e4b                  # chat: text, images, audio, tools, thinking (6.6–9.5 GB by runner; 9.5 GB on Apple Silicon)
ollama pull embeddinggemma-2:740m-q8_0  # embeddings of text, images and audio (1.3 GB)
ollama pull qwen2.5-coder:1.5b-base     # fill in the middle (986 MB)

A model's name is model:tag, and a name without a tag means its latest tag (model names): embeddinggemma-2 alone pulls a different 740m build, which was not measured here, so the examples name the tags they ran on. To run a local model with Ollama, ollama pull gemma4:e4b, then pass service=OllamaEndpoint(), model="gemma4:e4b"; Ollama has no default model. A Chat, Respond, Embeddings, FIM or transcription request that names none throws ArgumentError before anything is sent, and the Chat's message says what to name:

refusal = try Chat(service=OllamaEndpoint()); nothing catch err; err end
refusal isa ArgumentError || error("expected the Chat to be refused")
print(refusal.msg)

OllamaEndpoint() reads OLLAMA_HOST (optional; default http://127.0.0.1:11434) each time it is built. A host without a scheme is reached over http on port 11434 (gpu-box becomes http://gpu-box:11434), an http:// or https:// address without a port on port 80 or 443, the bind-all addresses 0.0.0.0 and :: on the loopback address, and ollama.com, given without a scheme, over https on port 443; an IPv6 address may be bare or bracketed, and a path is kept. A value UniLM cannot read this way, another scheme or a port outside 1–65535, throws ArgumentError when the endpoint is built. The endpoint's other arguments are on Options.

Ollama's local API "does not require authentication", and UniLM sends a server of your own no key. Direct cloud inference at https://ollama.com/api and https://ollama.com/v1 "requires an API key", used "in the Authorization: Bearer header" (authentication), and Ollama lists the cloud's models without one, curl https://ollama.com/api/tags (cloud). An endpoint whose server is https://ollama.com, as OLLAMA_HOST=ollama.com makes it, sends the OLLAMA_API_KEY environment variable that way whenever it is set, read each time a request is built, and to no other host. With the variable unset or blank, an inference request is not sent: the call returns a call error whose cause is an ArgumentError naming OLLAMA_API_KEY; list_models, model_info, running_models, pull_model and delete_model go without it. No request was sent to the cloud for this page (its requests bill). A cloud model runs through the local server once you sign in with ollama signin, under a cloud tag such as gemma4:cloud; Cost and usage says how UniLM prices it.

First call

A Chat starts with its system message; chatrequest! sends it and returns a typed result, and text reads the reply — or throws, on a failure:

chat = Chat(service=OllamaEndpoint(), model="gemma4:e4b", reasoning_effort="none")
push!(chat, Message(Val(:system), "You are a concise assistant."))
push!(chat, Message(Val(:user), "In one sentence: why run a language model locally?"))
result = chatrequest!(chat)
text(result)

result.message.finish_reason, result.model

u = result.usage
(; u.prompt_tokens, u.completion_tokens, u.cached_tokens, cost = estimated_cost(result))

reasoning_effort="none" turns Gemma 4's thinking off for a short answer (Reasoning). The reply's done_reason becomes finish_reason: "stop", or "length" for a reply that reached its max_tokens (sent as num_predict); a turn that carries tool calls reads "tool_calls" unless it was cut at "length". result.model is the "Model name used to generate this message" the reply gives (chat), the model estimated_cost prices; a cloud model whose reply drops its tag keeps the name requested (Cost and usage). Of the usage, prompt_tokens is Ollama's prompt_eval_count, "How many input tokens were in the prompt", cached_tokens its prompt_eval_cached_count, "How many prompt tokens were read from the cache", and completion_tokens its eval_count, the output tokens (usage), thinking included (Reasoning shows a count). The result types are on Results.

A local model's results cost 0.0, with no warning, unless you gave the model a price row (Cost and usage).

The first request to a model also loads it into memory: about 1.7 s for Gemma 4 E4B on an Apple M4 Max with 64 GB (Ollama 0.40.6), after which a short answer took about 0.1 s. load_model loads a model ahead of time (Models).

Conversations

A Chat keeps the conversation: each reply is appended to it, and the next chatrequest! sends the whole conversation again.

chat = Chat(service=OllamaEndpoint(), model="gemma4:e4b", reasoning_effort="none")
push!(chat, Message(Val(:system), "You are a concise assistant: answer in one short sentence."))
push!(chat, Message(Val(:user), "Which planet of the solar system is the largest?"))
text(chatrequest!(chat))

push!(chat, Message(Val(:user), "And the smallest?"))
text(chatrequest!(chat))

[m.role for m in chat.messages], cumulative_cost(chat)

The messages go out in the order they were pushed, each with its role, so a system message pushed later stays where it stands. An assistant turn goes back with its text, its thinking as thinking (Reasoning) and its tool calls with their ids; a tool result goes back with tool_name, the name of the function it answers, as Ollama's tool calling page sends results, and with its tool_call_id (Tools). A message with a name, and a tool result that answers no tool call of an earlier assistant turn, are refused before anything is sent (Limits and refusals); what push! refuses is the same on every provider (Conversations with Chat).

Streaming

With stream=true, chatrequest! returns a Task at once, and fetch gives the same typed result as an unstreamed call. The callback receives the text as it arrives, a String at a time, then the assembled Message:

chat = Chat(service=OllamaEndpoint(), model="gemma4:e4b", reasoning_effort="none", stream=true)
push!(chat, Message(Val(:system), "You are a concise assistant."))
push!(chat, Message(Val(:user), "List the planets of the solar system in order, one per line."))
deltas = String[]
task = chatrequest!(chat; callback=(chunk, close) -> chunk isa String && push!(deltas, chunk))
result = fetch(task)
text(result)

length(deltas), result.usage.completion_tokens, estimated_cost(result)

Ollama streams "newline-delimited JSON", one object per line (streaming), and sends the usage "as part of the final chunk, where done is true" (usage), so a streamed turn has usage with no stream_options, a field this endpoint refuses (Limits and refusals). Setting close[] = true stops the stream (Stopping a Stream Early).

  • End. The turn is final at the line whose done is true: the Message reaches the callback then.
  • Thinking. No thinking reaches the callback, only text: the thinking is assembled into the provider_content of the Message the callback receives last, where reasoning_text reads it, and goes back with the next request as an unstreamed turn's does.
  • Tool calls. A line carries whole tool calls, so on_tool_call(tc) runs as soon as the line that holds a call arrives.
  • Errors. "If an error occurs mid-stream, the error will be returned as an object" with an error property, and the status stays 200 (errors): UniLM ends the call with an LLMCallError holding it (When something fails).
  • Silence. A stream receives nothing while Ollama loads the model or while the request waits its turn behind others, which Ollama queues (FAQ), and stream_idle_timeout bounds that wait too (When something fails).

The concepts every provider shares are on Streaming.

Tools

Each Tool in tools goes out as a function tool with its name, description and parameters. tool_loop! runs the calls and sends their results back until the model answers in text:

city = Dict("type" => "object", "required" => ["city"],
            "properties" => Dict("city" => Dict("type" => "string")))
weather = UniLM.CallableTool(
    Tool(func=FunctionSignature(name="get_weather",
                                description="Current weather in a city",
                                parameters=city)),
    (name, args) -> "18°C and sunny in $(args["city"])")

chat = Chat(service=OllamaEndpoint(), model="gemma4:e4b", tools=[weather],
            temperature=0.0)
push!(chat, Message(Val(:system), "You are concise."))
push!(chat, Message(Val(:user), "What's the weather in Lyon? " *
    "Use the tool, then answer in one sentence."))

loop = tool_loop!(chat; tools=[weather])
calls = [(o.tool_name, o.arguments) for o in loop.tool_calls]
loop.completed, calls, text(loop.response)

call = chat.messages[3]   # the turn that called the tool
call.tool_calls[1].id, reasoning_text(call) !== nothing

Ollama has no tool_choice: the model decides whether to call a tool, so a tool_choice other than "auto" is refused, and it may call several tools in one turn — Ollama's tool calling page shows parallel calls — whatever parallel_tool_calls says: UniLM does not send it. Ollama's tool definition has name, description and parameters and no strict flag (API reference), so a tool marked strict=true is refused too (Limits and refusals).

Ollama's replies carry an id for each call, call_mb4i6gbs above, though its API reference lists none; UniLM sends the id back with the call and with its result, beside tool_name. A call that arrives without an id gets unilm_call_<k>, which is never sent: its result is matched by the function's name alone. The turn that called the tool also thought first, and that thinking went back with it (Reasoning). A streamed turn's tool calls are on Streaming, and the loop every provider shares is on Tool Calling.

Structured output

A response_format becomes Ollama's format: a JSON Schema format sends its schema, and UniLM.json_object() sends {"type": "object"}, the schema of any JSON object. Only the schema goes out; the format's name, description and strict have no counterpart in format (structured outputs: "Provide a JSON schema to the format field").

schema = Dict("type" => "object", "additionalProperties" => false,
              "required" => ["name", "year", "city"],
              "properties" => Dict("name" => Dict("type" => "string"),
                                   "year" => Dict("type" => "integer"),
                                   "city" => Dict("type" => "string")))

person = UniLM.json_schema("person", "A person", schema)
chat = Chat(service=OllamaEndpoint(), model="gemma4:e4b",
            response_format=person)
push!(chat, Message(Val(:system), "You extract facts."))
push!(chat, Message(Val(:user),
    "Extract the person: Ada Lovelace, born 1815 in London."))

using JSON
JSON.parse(text(chatrequest!(chat)))

With a response_format, the request turns thinking off (think: false), and a response_format together with a thinking effort (any effort but "none") is refused before the request is sent (Limits and refusals). UniLM's reason, which its message gives: Ollama applies a format only once the model's thinking ends, so a reply that skips thinking is not constrained at all — in the measurements below, every reply that was not valid JSON came from a run with thinking on in which the model did not think. A format limits which tokens the model may emit, not how many, so a reply can run on without closing the object. Give a structured-output request a max_tokens (sent as num_predict): a reply that reaches it stops with finish_reason "length" and is not complete JSON, instead of generating until the request times out. Ollama's page says its cloud "currently does not support structured outputs", and UniLM sends a cloud model's format all the same. The formats every provider shares are on Structured Output.

Evidence

The extraction request above, sent to /api/chat 10 times per setting on Ollama 0.34.4: gemma4:e4b returned valid JSON in 0 of 10 runs with thinking at its default (it answered plain text), 1 of 10 with thinking on, and 10 of 10 with it off; gemma4:e2b in 10, 8 and 10 of 10. Every failure was a run in which the model did not think. Without max_tokens, the same request on Ollama 0.40.6 twice generated until the 600 s default request timeout (more than 60,000 tokens in one run); the retry answered in under a second.

Reasoning

reasoning_effort becomes Ollama's think: "none" sends false, and every other effort goes as it is, "max" among them, a level of think in Ollama's API reference; a request without one sends none, so the model's default applies, and Gemma 4 thinks by default. Ollama's thinking levels are the model's own: /api/show lists the values a model takes and its default, and a model whose values are true and false thinks or does not; "If the model resolves named levels from /api/show metadata, Ollama applies supported names exactly. Unsupported names use the model default." (thinking). model_info reads them as thinking_levels and thinking_default: [false, true] and true for Gemma 4 E4B, which names no levels. No page says what such a model does with a named level on /api/chat; on Ollama 0.40.11, think "low", "medium" and "high" gave gemma4:e4b the same thinking and the same answer to the bat-and-ball prompt below at temperature 0 (observed on 25 October 2026), and a think: "max" request to gemma4:e4b was answered with HTTP 200, an answer without thinking, in the one request sent that day. To a model without thinking metadata, /api/chat answers a name other than "low", "medium", "high" and "max", such as "minimal" or "xhigh", with HTTP 400 invalid think value (Ollama 0.40.11: qwen2.5-coder:1.5b-base, whose /api/show reports no thinking, on 25 October 2026). respond's /v1/responses reads "minimal" as "low" and "xhigh" as "max" for such a model; there, "Boolean-only models that support enabling thinking map recognized compatibility efforts to true", so a model whose values are true and false, Gemma 4 E4B among them, takes any effort but "none" as true, and GPT-OSS reads "minimal" as "low" and "xhigh" as "high" (OpenAI compatibility). The thinking comes back beside the answer, and reasoning_text reads it:

chat = Chat(service=OllamaEndpoint(), model="gemma4:e4b",
            reasoning_effort="low", temperature=0.0)
push!(chat, Message(Val(:system), "You are concise."))
push!(chat, Message(Val(:user),
    "A bat and a ball cost 1.10 in total. The bat costs 1.00 more " *
    "than the ball. How much does the ball cost? " *
    "Answer with the number only."))
result = chatrequest!(chat)
text(result)

print(first(reasoning_text(result), 300), "…")

result.usage.completion_tokens

reasoning_text gives the turn's thinking, or nothing for a turn without one, and the output count holds the thinking as well as the few characters of the answer. The thinking stays on its turn in the Chat and goes back to Ollama with the next request, which renders the conversation for the model itself (Gemma 4's page: "Ollama already handles the complexities of the chat template for you"). Gemma 4's guidance asks that "Thoughts from previous model turns must not be added before the next user turn begins" (Gemma 4); in a tool round trip measured with gemma4:e2b on Ollama 0.34.4, the turn succeeded 10 of 10 times with the thinking sent back and 8 of 10 without it. Thinking spends the reply's token budget first: a small max_tokens can end a reply at finish reason "length" with no answer text.

A thinking model decides when to think

With thinking on, Gemma 4 E4B still answers easy prompts without thinking: reasoning_text is then nothing. On the bat-and-ball prompt above (Ollama 0.34.4) it thought in 2 to 5 of 6 runs at the default temperature, and in every run at temperature=0.0.

Attachments

A user message carries images and sound clips as attachments, read from a file or from bytes and recognised by their content: an ImageAttachment (PNG, JPEG, GIF or WebP) or an AudioAttachment (WAV or MP3). Each goes out as a base64 entry of the message's images, the form Ollama's API takes: "the REST API expects base64-encoded image data" (vision), so a model never fetches an image itself.

chat = Chat(service=OllamaEndpoint(), model="gemma4:e4b", temperature=0.0)
push!(chat, Message(Val(:system), "You are concise."))
push!(chat, Message(Val(:user), "What colour is the shape? One word.",
                    ImageAttachment("../../assets/red_circle.png")))
text(chatrequest!(chat))

The recording says "The secret word is banana.":

chat = Chat(service=OllamaEndpoint(), model="gemma4:e4b", temperature=0.0)
push!(chat, Message(Val(:system), "You are concise."))
push!(chat, Message(Val(:user),
    "What is the secret word in this recording? One word.",
    AudioAttachment("../../assets/secret_word.wav")))
text(chatrequest!(chat))

Ollama's Gemma 4 page lists text, image and audio for E2B and E4B, and text and image for the 26B and 31B models. model_info lists what an installed model takes, :vision and :audio among its capabilities (Models); UniLM checks neither, and a model without the capability answers with an HTTP 400 once it has been loaded: on Ollama 0.40.11, qwen2.5-coder:1.5b-base loaded and then answered an image with "Multimodal data provided, but model does not support multimodal requests." (When something fails). A DocumentAttachment and an image's detail level are refused before the request: the images entry has room for neither (Limits and refusals). The attachment types are on Attachments.

Audio

Of UniLM's audio verbs, only transcribe reaches Ollama: a model that hears audio transcribes it, while speak and translate refuse the endpoint before sending anything. A transcription is not recorded by with_recorded_answers, so its output here is quoted from a live run:

r = transcribe("secret_word.wav"; service=OllamaEndpoint(), model="gemma4:e4b")
r isa TranscriptionSuccess || error("the transcription failed: $r")
transcript_text(r)
# Transcribed on 25 October 2026 with UniLM's development branch after 0.26.0 and Ollama 0.40.11,
# the recording above:
# "The secret word is banana"

The request goes to /v1/audio/transcriptions, a route Ollama's OpenAI compatibility page does not list; Ollama 0.40.11 answered it, as above. There is no default model: name one that hears. Ollama transcribes at temperature 0 and reads one language and a prompt (by Ollama 0.40.6's source). UniLM asks for the transcript as JSON, the only form in which Ollama reports a failure that arrives after its reply has begun, as an AudioCallError (by the same source; untested), and reads the reply as JSON, though Ollama labels it application/x-ndjson. response_format = "text" is refused before the request, since such a failure would read as an empty transcript: leave response_format unset and read the text with transcript_text. temperature, languages, keywords and any other format are refused too (Limits and refusals). A transcription is sent again after a transient status, as a chat request is, the whole file each time.

respond and FIM

respond reaches Ollama's /v1/responses, which serves "Only the non-stateful flavor" of the Responses API: "there is no previous_response_id or conversation support" (OpenAI compatibility). Each call is answered and forgotten:

result = respond("In one sentence: what is a prime number?"; service=OllamaEndpoint(),
                 model="gemma4:e4b", instructions="You are a concise assistant.",
                 reasoning=Reasoning(effort="none"))
output_text(result)

u = token_usage(result)
(; result.response.status, u.prompt_tokens, u.completion_tokens, cost = estimated_cost(result))

Of a Respond, UniLM sends model, input, instructions, function tools, tool_choice "auto", temperature, top_p, max_output_tokens, stream, a text format and the effort of reasoning, and refuses every other field before the request rather than have Ollama drop it: the fields that need a stored response (store, previous_response_id, background, conversation), the other fields its compatibility page does not list as supported, and seed, which a Chat sends to Ollama instead (Limits and refusals). Ollama's page lists no text field either; UniLM sends a json_schema text format with its schema, which Ollama 0.40.11 followed in the one such request sent on 25 October 2026, and, as for a Chat, such a format turns thinking off (reasoning.effort "none") and refuses a thinking effort. Cap a request with max_output_tokens: Ollama reports a reply cut at that limit as "completed", with no incomplete_details (Ollama 0.40.8), so a reply whose output tokens (token_usage) reach the limit is the cut one. A Respond tool loop, get_response, cancel_response, delete_response and list_input_items are refused before any request, since Ollama stores no response: run a tool loop on a Chat with tool_loop!. compact_response reaches /v1/responses/compact, a route the compatibility page does not list, which Ollama 0.40.11 answered with a compaction item (observed on 25 October 2026), and, like a Chat, needs a model: a call that names none throws before any request.

fim_complete reaches /v1/completions with a prompt and the suffix the reply fills up to, on a model that fills in the middle, one whose capabilities include :insert, such as qwen2.5-coder:1.5b-base (Gemma 4 E4B's do not):

result = fim_complete("def area(r):\n    "; suffix="\n    return a\n", service=OllamaEndpoint(),
                      model="qwen2.5-coder:1.5b-base", max_tokens=32, temperature=0.0)
fim_text(result)

The completions route takes suffix among its fields (OpenAI compatibility), and a FIM request has no default model. These routes carry none of the endpoint's keep_alive, options or runner (Options). A local model's respond and FIM results cost 0.0 unless you price the model, as its chats do (Cost and usage); the verbs every provider shares are on Agentic respond and FIM & Prefix Completion.

Cost and usage

A local model bills no one, so estimated_cost gives 0.0 for a chat, embeddings, respond or FIM result, without the missing-price warning other unlisted models get, and cumulative_cost adds 0.0 for each turn; pass model= to price one as if it had run elsewhere, at that model's row. To price a local model yourself, give its exact name a row: one in pricing= prices estimated_cost, and one you add to DEFAULT_PRICING prices both. The rows UniLM ships price hosted models only, so a model copied under a hosted model's name with ollama cp, as Ollama's OpenAI compatibility page suggests for tools that expect such names, still costs 0.0, also with a copy of those rows such as merge(DEFAULT_PRICING, …). A cloud model reached through the same server — one whose tag is cloud or ends in -cloud, such as gemma4:cloud or gpt-oss:120b-cloud — runs in Ollama's cloud, and UniLM prices each of its results by the requested name, like any other model, never as a free local call; a name missing from the price table gets the missing-price warning. So does every model a request to Ollama's cloud itself names — an endpoint whose server is https://ollama.com (Setup) — whose names carry no cloud tag, "such as gemma4:31b" (cloud). A cloud reply may name the model without its tag, gpt-oss:120b (by Ollama 0.40.6's source, which sends the cloud the name without it; untested, as no cloud call was made): a chat, System One, respond or FIM result keeps the requested name — a System One, respond or FIM result keeps the server's in its raw — while an embeddings result is priced by the model its request names. Through your own server, UniLM recognises a cloud model by its tag alone, so one copied under a name without it (ollama cp) is priced as local: 0.0, with no warning, unless you gave it a row. How a call is priced on every provider is on Cost Tracking.

Limits and refusals

A request meets the model's context window, which the endpoint's num_ctx sets when the model loads: by default a chat prompt that does not fit is an HTTP 400 on the :llamacpp runner, not a silently shortened prompt, while a model on the :mlx runner answers it (Ollama 0.40.6; Runners). UniLM checks no size itself: not the window, not the length of a sound clip, not an image's size. An embeddings input longer than the model's window is the server's HTTP 400 too (Long inputs).

A Chat field UniLM maps to no part of the /api/chat request is refused, not dropped, since dropping it would send a request other than the one asked for, and so is each request below that Ollama would answer with an error or run other than asked. The verbs throw these ArgumentErrors before anything is sent. Building the endpoint refuses an argument that breaks its rule (Options).
