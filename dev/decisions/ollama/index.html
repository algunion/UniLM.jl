Decisions · Local decision models

Local decision models

Ollama serves decision models on your own machine — Tev1, Nimble, Kev, Clef Flash, Strands Decider and the others it lists as decision models — through its System One route, POST /v1/systemone, which answers choice, yes/no and scoring questions about a state with probabilities and writes no text (System One); no key is sent to a server of your own, and a local model costs nothing unless you price it. OllamaEndpoint(), the endpoint of the Ollama language-model entry, sends ask and the verbs built on it there, and no decision verb refuses it. Of the route, UniLM does not wrap a keep_alive given as a duration string; a cloud model reached through your local server takes the same requests as a local one, and a request to Ollama's cloud itself, https://ollama.com, carries the OLLAMA_API_KEY its inference needs and is not sent without it (Setup).

Setup

Run Ollama, the desktop app or ollama serve, and pull a decision model:

ollama pull tev1:0.8b        # the model this page's text examples run on
ollama pull tev1:4b          # the most accurate of the nine measured below
ollama pull clef-flash:9b    # pictures

Ollama 0.35.0 or later serves the route, and the Clef models, which read pictures, need 0.35.1 or later (Decision); from 0.40.0, Nimble, Tev1, Clef and Clef Flash run on MLX on Apple silicon (v0.40.0), and a cloud model through the local server needs 0.40.5 (System One). This page's measurements ran on Ollama 0.40.6, and its new examples on 0.40.11.

A call goes to Ollama when it names service = OllamaEndpoint(), or when it names no service and a with_system_one(OllamaEndpoint(); model = …) scope encloses it. Ollama has no default model: a call names an installed decision model with model = …, or, when it names no service, takes the scope's; a call left with no model is refused before anything is sent (Limits and refusals). OllamaEndpoint() reads OLLAMA_HOST when it is built, else http://127.0.0.1:11434 (Setup); no key is sent to a server of your own.

Options

Of an OllamaEndpoint's arguments, a decision request carries three: its base_url, its keep_alive unless the call names one, and its runner. Its other arguments — truncate, shift and the OllamaOptions such as num_ctx — have no field on this route and are not sent, so the window is the one the model is loaded with, and "input is never truncated" (System One); load_model loads a decision model without them too (Models). The constructor's checks are on Options.

  • keep_alive, the one request option, is a keyword of ask and ask_each — options = (keep_alive = …,) on the natural-language verbs, a keyword of with_system_one for a scope —, else the endpoint's own: the seconds the model stays loaded after the request, 0 to unload it at once and Inf to keep it loaded, which UniLM sends as -1, the negative value Ollama reads as "keeps it loaded". Unset, Ollama's default applies, "5m unless configured otherwise" (System One). It changes how long a model stays in memory, never an answer, so it is not part of a recording's key.
  • runner, an argument of the endpoint, goes with every decision request and is part of a recording's key. Leave it unset, or pin per model the runner its listing names (OllamaModel.runner): OllamaEndpoint(runner = :llamacpp) with model = "kev:0.8b-q8_0". A runner the model has no build for is the server's HTTP 400 no compatible manifest found for runners: <runner>, never a fallback (Runners).

First decision

One request carries the state once and every question about it; each answer comes back under the name you gave its question:

const TEAM = (billing   = "payments, charges, invoices or refunds",
              technical = "the app or the website does not work as expected",
              shipping  = "a parcel that is late, lost or arrived damaged",
              other     = "anything else")
message = "I was charged twice for order #4471. Please refund the duplicate payment."

r = ask(message, "team" => choice("Which team should handle this message?", TEAM);
        service = OllamaEndpoint(), model = "tev1:0.8b")
a = r["team"]
(a.choice, a.probabilities[a.choice], a.confidence)

a.choice is the most probable option, a.probabilities holds one probability per option, and a.confidence says how peaked they are, which UniLM computes (Confidence and tuning). A failed call has no answers: r["team"] throws a SystemOneError on it (When something fails).

r.response.model, token_usage(r).prompt_tokens, r.response.request_id, estimated_cost(r)

r.response.model is the model the request named, Ollama sends no request id, and a local model's answer costs 0.0, with no warning, unless you gave the model's exact name a price row, in pricing= or added to DEFAULT_PRICING; a row UniLM ships for a hosted model never prices a local model that bears its name. A cloud model reached through the server — a tag of cloud, or one ending in -cloud — is priced by the requested name instead, as is every model a request to Ollama's cloud itself names (an endpoint whose server is https://ollama.com); UniLM's price table holds no row for one, so estimated_cost gives 0.0 with a warning that the row is missing (Cost Tracking). nl_classify makes the same kind of decision in one call and returns the key whose description fits (Dispatch on Meaning):

nl_classify(message, TEAM; service = OllamaEndpoint(), model = "tev1:0.8b")

Models

On 25 October 2026 Ollama lists ten decision models: d3, tev1, nimble, clef, clef-flash, nimble-v3, pplx-decider, kev, laya and strands-decider; clef also runs in Ollama's cloud. The d1 and d1-omni models measured below are decision models by their own pages, with text and image input (d1, d1-omni). A model's name is model:tag; name the tag you measured, since a name without one means its latest tag (Setup). The model that answered is the one the request named: Ollama documents the reply's model as the "Model name from the request", and a cloud model whose reply drops its tag keeps the requested name in r.response.model, the reply's in raw.

Nine decision models answered the same 129 labelled support tickets, one Choice of seven intents each, through UniLM on one machine:

  • Most accurate: tev1:4b, right on 0.938 of the tickets and the best calibrated of the nine (expected calibration error 0.038), in about 0.24 s a ticket.
  • Small and fast: d1-omni:600m, 0.868 in 0.025 s, and strands-decider:2b, 0.899 in 0.084 s.
  • Pictures: clef-flash:9b, 0.915 on these text tickets in 0.64 s, or d1:3b, 0.845 in 0.14 s, on the llamacpp runner where MLX does not run.
  • kev:9b-q4_K_M is nearly as accurate (0.922), but its probabilities are poorly calibrated (0.145); kev:0.8b-q8_0 was right on 0.690.

Each model's answer was the one Ollama sent: UniLM's probabilities equalled the server's reply to the same bytes, on all nine. How the hosted providers did on the same tickets is on Choosing a decision provider.

Questions

The route answers three kinds of question, in any mix in one request (System One): a choice picks one option, a score places the state on levels lowest first, and a noul gives the probability that a statement holds, its yes and no sent as the descriptions of "true" and "false". A RawQuestion is sent as written, for the server to judge; a box is refused (Limits and refusals). No answer is passed to a later question: "Answers are not passed to later questions" (System One). By Ollama's source at v0.40.11, though, every prompt for Nimble and Clef holds all the questions of the request, Clef's under "Decide every field jointly" (decision/prompts.go, decision/clef.go), while a Tev1 prompt holds its own question alone.

q = ask("The app crashes every time I open my order history. Third time this week, and my parcel is due today!",
        "team"    => choice("Which team should handle this message?", TEAM),
        "urgency" => score("How urgent is this message?",
                           ["Can wait", "Needs attention this week", "Needs attention today"]),
        "repeat"  => noul("Has the customer had this problem before?");
        service = OllamaEndpoint(), model = "tev1:0.8b")
(q["team"].choice, q["urgency"].score, q["repeat"].noul)

What reaches the model depends on the model, since each family has its own prompt:

  • Question names travel, and may be read. The request keys its questions by name. By Ollama's source, the prompt it builds for Nimble ends with the question's name, while Tev1's holds only the state, the instructions and the options (decision/prompts.go): write the whole question in its instructions.
  • Option names and descriptions both travel. A Choice's criteria map each option to its description, or to no description for a bare name.
  • Give every question instructions. Ollama's API reference lists instructions as required for each question, and UniLM refuses a question without them before sending (Limits and refusals). Instructions may be a string, an object or an array; an option's description, a Score level and a Noul's yes and no are strings.

The route takes 1 to 64 questions, a Choice of 2 to 255 options and a Score of 2 to 10 levels, and a model may take fewer: the limits, and what each model measured takes, are on Limits and refusals. Reading the answers and the decision rules on them are on Route and Decide.

The natural-language verbs ask one Choice of the meanings you write. nl_dispatch sends the arguments it dispatches on as a JSON object, which the route takes as the state, and @branch its state as it is; with no model of their own they are refused like any call (Limits and refusals):

route(::nl"the customer wants a refund", msg)           = :refunds
route(::nl"the customer reports a bug in the app", msg) = :engineering
route(::nl"anything else", msg)                         = :frontline

nl_dispatch(route, message; service = OllamaEndpoint(), model = "tev1:0.8b")

@branch message service = OllamaEndpoint() model = "tev1:0.8b" begin
    "the customer wants a refund"           => :refunds
    "the customer reports a bug in the app" => :engineering
end

Images

A vision decision model answers questions about pictures: Clef and Clef Flash read PNG, JPEG and WebP images, from Ollama 0.35.1 (Decision), and the pages of d1 and d1-omni list image input. Measured here: clef-flash:9b, d1:3b and d1-omni:600m; other decision models whose model_info capabilities include :vision take the same request, untested. The pictures go first in the state, then its texts:

photo = ImageAttachment("../assets/red_circle.png")
r = ask([photo, "A photo sent in with a return."],
        "colour" => choice("What colour is the shape?", ["red", "green", "blue"]),
        "round"  => noul("Is the shape round?");
        service = OllamaEndpoint(), model = "clef-flash:9b")
(r["colour"].choice, round(r["colour"].confidence; digits = 3), round(r["round"].noul; digits = 3))

One request asked both questions about the picture: clef-flash:9b saw red, at a confidence of 0.991, and gave "Is the shape round?" a probability of 0.945.

  • How they are sent. Ollama takes a request's pictures as one list, images, base64-encoded and "shared by all questions, in request order" (System One), and by its source Clef reads them before the state's text (decision/clef.go). So the state is a picture, or a vector or a tuple of pictures followed by texts; the texts become the request's state — none: an empty string, one: that string, several: an array — and a blank text beside pictures is sent, as Ollama's source accepts an empty state that comes with pictures (decision/systemone.go).
  • Refused before sending: a picture after a text, which Clef would read first; a picture inside a JSON object or array (to nl_dispatch, which sends its arguments inside an object, pass state = [image, …texts]); pictures beside values that are not texts; a picture in a question (Limits and refusals).
  • A model without vision answers with its own HTTP 400, a SystemOneFailure carrying the model's own words (When something fails): check status == 400, not the text.
  • Cost and usage. A local model's answer costs nothing unless you price the model; the reply's input_tokens counts the pictures' token positions (System One).
  • Recordings key and store each picture by its SHA-256, never its bytes (Testing and recordings).
  • d1-omni:600m takes pictures but read them unreliably: it called a red square "blue" (probability 0.954), and gave "Is there a red shape?" about the red circle a probability of 0.0000006. For pictures, prefer clef-flash:9b, or d1:3b where MLX does not run.

Confidence and tuning

Ollama documents its confidence as "Distribution concentration, calculated as 1 - H(p) / ln(N)", an entropy measure that is "Not calibrated correctness" (System One). UniLM does not pass it on: so that a threshold means the same on every provider, it computes confidence from the returned probabilities — (n·p_max − 1)/(n − 1) for a Choice of n options, clamped to 0 … 1, as on Reading answers, and 1 − Σᵢ pᵢ·|i − m| / MAD_unif for a Score whose most likely level is m, floored at 0 (Confidence); one outcome gives 1 — and keeps the server's value in the answer's raw:

const MESSAGES = [
    "I was charged twice for order #4471. Please refund the duplicate payment.",
    "The app crashes every time I open my order history. iPhone 15, latest version.",
    "My parcel was due last Monday and the tracking hasn't moved in six days.",
    "Do you ship to Norway, and how much does delivery cost?",
    "The phone I received has a cracked screen and the box was crushed. I want my money back.",
    "Your update deleted my saved addresses and now I can't check out. Third time this month!",
]

seen = SystemOneSuccess[]
team = nl_classify(MESSAGES[5], TEAM; service = OllamaEndpoint(), model = "tev1:0.8b", min_confidence = 0.6,
                   fallback = message -> :person, on_response = r -> push!(seen, r))
answered = only(seen)["classify"]
(team, round(maximum(values(answered.probabilities)); digits = 3), round(answered.confidence; digits = 3),
 round(answered.raw["confidence"]; digits = 3))

tev1 put 0.534 of the probability on billing, out of four options: the formula above makes that a confidence of (4 × 0.5337 − 1)/3 ≈ 0.378, below the 0.6 asked for, so the message went to a person; the entropy measure Ollama reports reads the same answer as 0.375. The two measures part most on a peaked answer: tev1's answer about shipping to Norway, 0.811 on other, is 0.748 by the formula and 0.638 by the entropy (One formula, calibrated per model).

Probabilities are accepted when they sum to 1 within 0.00005 per outcome, since Kev models on Ollama's own runner round each to four decimals, and the chosen option when it lies at most 0.0001 below the most probable; a reply further off is a SystemOneCallError.

  • Gate on confidence, not on raw["confidence"], when a threshold must mean what it means on another provider.
  • Tune min_confidence per model, on labelled messages of your own: the same bar hands a different share of the work to a person on each model. Where some mistakes cost more than others, price each one and let a decide policy choose the cheapest action (When mistakes have different prices), once you have checked that the model's probabilities are calibrated (Models).
  • Pin the model's tag, and its runner where it has builds for several: the answers are the build's.
Evidence

Measured on Ollama 0.40.6, an Apple M4 Max, 21 October 2026: the five MLX models (tev1:0.8b, tev1:4b, nimble:9b, strands-decider:2b, clef-flash:9b) reported the entropy measure, while Kev and the models on the llama.cpp runner (kev, d1, d1-omni) reported the Choice formula above. Repeated runs of the 129 tickets gave the same answer to every ticket, and in UniLM's live test suite on the nine models every probability distribution summed to 1 within 4.4e-16.

Testing and recordings

with_recorded_answers records an exchange with Ollama's route once and replays it with no server: ask, ask_each and the verbs built on them. A recording is filed under /ollama/v1/systemone, the request's path behind the namespace ollama, and keyed on the exact request: its method, that path, and its body, which names the model and, when the endpoint sets one, the runner. keep_alive is sent and left out of the key and the file, and a picture is keyed and written as data:<mime>;sha256,<hex>, the SHA-256 of its base64 text, never its bytes.

recordings = mktempdir()      # in a package: a directory committed next to the tests
recorded = with_recorded_answers(recordings; mode = :record) do
    ask(message, "team" => choice("Which team should handle this message?", TEAM);
        service = OllamaEndpoint(), model = "tev1:0.8b")
end
JSON.parsefile(only(readdir(recordings; join = true)))["request"]["path"]

replayed = with_recorded_answers(recordings) do
    ask(message, "team" => choice("Which team should handle this message?", TEAM);
        service = OllamaEndpoint(base_url = "http://127.0.0.1:9"), model = "tev1:0.8b", keep_alive = 0)
end
replayed["team"].probabilities == recorded["team"].probabilities

The replay names another host, where no server runs, and a keep_alive the recording did not, and is answered from the recording: neither is part of the key. Recording takes a running server with the model pulled, and replaying takes nothing; in this manual's build the recording scope above replays the manual's own recordings, so the example reaches no server either (How this manual runs its examples). list_models on Ollama is not recorded: inside a scope it goes to the server, as outside one.

  • What a recording cannot hold. To test what your code does with an answer the model rarely gives — a near-tie, a failed call, an option it was never offered — point an OllamaEndpoint at a local server that answers what you wrote, in the route's shape. Run such tests outside with_recorded_answers. This block is not run when the manual is built:
using UniLM, HTTP, JSON, Test

route(::nl"the customer wants a refund", msg)           = :refunds
route(::nl"the customer reports a bug in the app", msg) = :engineering
route(::nl"anything else", msg)                         = :frontline

canned = Ref{Any}()                  # (status, body) the server answers next
server = HTTP.serve!("127.0.0.1", 8125; verbose = false) do req
    status, body = canned[]
    HTTP.Response(status, ["Content-Type" => "application/json"], JSON.json(body))
end
mock = OllamaEndpoint(base_url = "http://127.0.0.1:8125")

# A 200 in the route's shape: the one question is "meaning_1"; `option` gets probability p.
const OPTIONS = meanings(route, Tuple{String})[1]
choosing(option, p) = (200, (model = "tev1:0.8b", usage = (input_tokens = 96, output_tokens = 0),
    answers = (meaning_1 = (type = "choice", choice = option, confidence = 0.5,
                            probabilities = Dict(o => o == option ? p : (1 - p) / (length(OPTIONS) - 1)
                                                 for o in OPTIONS)),)))

@testset "route on a local decision model" begin
    canned[] = choosing("the customer wants a refund", 0.97)
    @test nl_dispatch(route, "I want my money back."; service = mock, model = "tev1:0.8b") === :refunds

    canned[] = choosing("the customer wants a refund", 0.40)      # a confidence of 0.1 by UniLM's formula
    @test nl_dispatch(route, "Hm."; service = mock, model = "tev1:0.8b",
                      min_confidence = 0.7, fallback = m -> :human) === :human

    canned[] = (404, (error = "model 'tev1:0.8b' not found",))
    @test_throws SystemOneError nl_dispatch(route, "Hm."; service = mock, model = "tev1:0.8b")
end
close(server)

The reply's confidence there is ignored: UniLM computes its own from the probabilities. An answer outside the offered options makes the call a SystemOneCallError, so nl_dispatch throws a SystemOneError, and no method runs.

Throughput

ask_each sends one request per item and returns the results in input order; on Ollama it keeps one request in flight unless its ntasks says otherwise, as a local decision runner may serve one request at a time: Ollama starts Nimble's for one (#18750). How a batch backs off when a server is busy is on Many requests at once.

results = ask_each(MESSAGES, "team" => choice("Which team should handle this message?", collect(TEAM));
                   service = OllamaEndpoint(), model = "tev1:0.8b")
[(findfirst(==(r["team"].choice), TEAM), round(r["team"].confidence; digits = 2)) for r in results]

A request's questions may be scored one after another, so its latency grows with their number (#18750, open on 25 October 2026), and in the reply's input_tokens, "Shared context is counted again when the model scores questions separately" (System One). Keep the model loaded while a batch runs (keep_alive), and unload it when the batch is done; the first call loads it. Each model's warm latency, and its first call, are in the Evidence of Models.

When something fails

A call that reaches Ollama returns a SystemOneSuccess; a SystemOneFailure for a status other than 200, with the status and Ollama's message, and no request id; or a SystemOneCallError when no usable response came. A 200 whose answers do not fit the request — a question unanswered, an option that was not offered, probabilities that are no distribution within the rounding above — is a SystemOneCallError too. Reading an answer of a failed call (r["name"], answer, answers) throws a SystemOneError.

UniLM sends a request again after a 408, 429, 500, 502, 503, 504, 520 to 524 or 529, up to max_attempts times within total_deadline, waiting at least what a retry-after-ms header asks for, else a Retry-After; any other status comes back as it is. Ollama brings no bounds of its own, since loading a model on a CPU can take minutes: with no RequestConfig of yours, a call has the field defaults, 600 s per attempt and 900 s in all (Timeouts & Retries).
