Reference · API: decisions

System One API (Jev, OpenAI Decisions, Ollama)

A System One model does not write text. It reads a piece of state and answers the questions you enumerate with a probability distribution over the outcomes you named, already typed — a String option, a Float64 score, a probability, a box — so there is nothing to parse. The answer says what, the distribution says whether to act on it.

UniLM has one System One surface — ask, ask_each, the question builders and the typed answers below — over three backends: TypeSafe's Jev (the default), OpenAI's Decisions API (generally available) and local decision models served by Ollama. Route and Decide is the how-to and Choosing a decision provider compares the three. This page gives what every backend shares, then each backend's setup, rules, errors and cost, then every type and verb; nl_classify, nl_dispatch and @branch have a page of their own, Natural-Language Dispatch.

A call takes its backend from service = …; without one, from the enclosing with_system_one scope, which can also set the model of the calls that name none; outside every scope, from TypeSafe. ask, ask_each, list_models and the natural-language verbs resolve it alike. Any other endpoint that declares :system_one is a backend too, and one without a protocol of its own speaks TypeSafe's wire (Provider protocol).

The question types hold only what every backend requires. What a backend's wire cannot carry — more options or levels than it takes, a question kind, an image or an option it does not know — its wrapper refuses before anything is sent, with an ArgumentError naming the backend, the rule and the fix: choice builds a Choice of 256 options, and only sending it to a backend that takes fewer is refused. Every reply is checked against its request alike on every backend (see ask), with the backend's own allowance for how it rounds probabilities; a reply that does not fit is a SystemOneCallError.

confidence is one measure on every backend — (n·p_max − 1)/(n − 1) for a Choice over n options, 1 − Σᵢ pᵢ·|i − m| / MAD_unif for a Score whose most likely level is m (Confidence): TypeSafe and OpenAI report it, and the Ollama wrapper computes it from the probabilities; over a single option it is 1.0, as TypeSafe answers a one-option Choice. How far a confidence can be trusted is a property of the model, not of the formula.

Tune the confidence threshold per backend

A threshold tuned on one backend does not carry over to another. On the same 129 labelled support tickets with 7 options (2026-10-20), Jev (jev-1.13.0) chose the right option for 96.9% of them, with an expected calibration error of 0.016, and OpenAI's gpt-6-luna for 94.6%, with 0.080 — in every bin above 0.5 its accuracy was at least its mean top probability: it is under-confident. Tune a threshold on the backend, and the model version, it will run on (Choosing a decision provider).

While you set no RequestConfig of your own — no config, no with_request_config scope, no set_default_config! — a backend may bound its calls itself: TypeSafe's wire and OpenAI's by 60 s per attempt and 150 s in all, while Ollama brings no bound of its own, so the field defaults apply (loading a model on a CPU can take minutes). ask_each keeps at most 16 requests in flight on TypeSafe's wire and OpenAI's, 1 on Ollama and 8 on a protocol of your own, unless its ntasks says otherwise. Every System One exchange goes through one connection pool per process, which keeps up to 256 idle connections per host for 30 s, so a batch or a loop finds its connections open.

with_recorded_answers files each backend's exchanges apart: TypeSafe's under the request's path (/v1/systemone), OpenAI's under /openai-decisions/v1/decisions, Ollama's under /ollama/v1/systemone. A recording never replays for another backend; an endpoint that speaks TypeSafe's wire shares TypeSafe's recordings, since its requests are TypeSafe's. An option that changes how a request is served but never what it is answered — OpenAI's prompt_cache_key, safety_identifier and prompt_cache_options, Ollama's keep_alive — is sent and left out of the recording, key and file alike, so the same question replays whatever it is; TypeSafe's long_context is part of the key.

Models and versions

list_models returns the names the account may put in model:

m = list_models()
if m isa TypeSafeModelsSuccess
    for card in m.models
        println(card.name, "  ", card.release_date, "  ", card.description)
    end
else
    println("Request failed — ", m)
end

The listing holds aliases: jev-latest, the most recent stable release and the default here, and jev-preview, the most recent release of any kind, ahead of jev-latest when a preview build exists. A versioned id such as jev-1.13.0 is a valid model whether or not it is listed, and the listing is scoped to the account (Models). SystemOneResponse.model reports the versioned id that answered: log it, since an alias moving is otherwise invisible, and a threshold tuned against one version is a claim about that version only.

In October 2026 jev-latest answers as jev-1.13.0 and jev-preview as jev-1.14.0 (Jev 1.14, available from October 14, 2026). Both read images; a box question needs Jev 1.14 or later — model = "jev-1.14.0" or "jev-preview". Jev 1.13 answers a request with one with HTTP 400 and the bare message "Invalid request.", which ask returns with a hint naming those models. long_context = true works on both (Limits).

ask checks every limit but the context and the rate limits before the round trip, and refuses a request over one with an ArgumentError naming TypeSafe's limit and the value — a Choice of 256 options, a Score of 11 levels, a GIF, an image 2000 pixels wide, a file cut short within its header, a JPEG that does not end with its end-of-image marker (FF D9: cut short, or carrying bytes after the image), a state nested 65 levels deep. The question types themselves set no upper bound — other System One backends have other limits, which their wrappers check the same way — so choice and score build such questions; only sending one to TypeSafe is refused. A box question needs an image in the request to locate in, so one in a request without an image is refused as well: TypeSafe answers it anyway, with HTTP 200 and a box at a low confidence — 0.05 to 0.10 in probes on 2026-10-19 and 2026-10-20 — that locates nothing. A Box answer turned inside out (top > bottom or left > right) is a SystemOneCallError.

An ImageAttachment may stand anywhere in the state, the instructions or the criteria — a Choice whose options are example pictures, a Score whose levels are. TypeSafe marks images and Box questions "Dreamer-ready", not yet ready for production: their request format, answers and limits "can change between releases" (Images). Each distinct image is sent once, as a part of a multipart/form-data request, and every place it stood holds its reference, <image:…> with the first 32 hex digits of the SHA-256 of its bytes; every use is billed, so an image several questions need belongs in the state. A request with an image or a Box question carries the header TypeSafe-Danger-Zone-Images: true TypeSafe requires: passing one is the opt-in. A Score level that is an image comes back in the answer's legend as that same ImageAttachment. Images are numbered in an error message as they first occur: the state, then each question's instructions and criteria. TypeSafe applies no EXIF orientation, so rotate a photo's pixels upright before sending it. A recording of a request with images (with_recorded_answers) is keyed on its JSON part and the SHA-256 of each image, and holds no image.

long_context = true — ask(state, questions...; long_context = true) — sends TypeSafe-Danger-Zone-Long-Context: true, which raises both context limits to 262k tokens at the same price per token; TypeSafe documents it as slower and less accurate than the default limits, and the answer does not say which ran. A request over its context comes back as a 400 whose error_type is "max_tokens_exceeded", and its message names long_context and the limits.

Errors, timeouts and retries

A call that reaches the service returns a SystemOneSuccess, a SystemOneFailure (a status other than 200) or a SystemOneCallError (no usable response), and issuccess separates them; a wrong service or a malformed request is an ArgumentError before anything is sent. A 200 whose answers do not fit the request — a question unanswered, an answer of another kind, an option that was not offered, probabilities that are not a distribution over the offered outcomes, a value outside 0 … 1, a Score whose score its probabilities contradict or whose legend renames a level asked as a string, no model named — is a SystemOneCallError too, carrying the request id: no success is built from a malformed answer. TypeSafe's probabilities are accepted when they sum to 1 within 0.005 per outcome, and the chosen option when it lies at most 0.01 below the most probable: one live reply, a Choice of four options, summed to 0.99 — the mark of values rounded to two decimals. The service writes errors in three detail shapes: message is extracted from whichever arrived, and error_type is filled in only by the object shape.

state     = "Help! My payouts have been failing for 3 days."
questions = ["urgency" => score("How urgent is this ticket?",
                                ["Can wait", "Needs attention this week", "Needs attention today"])]

# Per call.
r = ask(state, questions; config = RequestConfig(request_timeout = 20.0, max_attempts = 5))

# Or for a whole scope, including tasks spawned inside it.
scoped = with_request_config(request_timeout = 20.0, max_attempts = 1) do
    ask(state, questions)
end

for res in (r, scoped)
    if res isa SystemOneSuccess
        println(answer(res, "urgency"))
    else
        println("Request failed — ", res)
    end
end

A timeout, a transport failure or a cancellation — through cancel= or the ambient with_cancel token, with a UniLMCancelled as the cause — is a SystemOneCallError, never a partial success (Timeouts & Retries, Concurrency, Tasks and Cancellation).

Cost

Only input tokens are billed; output tokens are currently free (Models). Every question in one call shares one ingestion of the state, so many questions in one ask cost far less than one call per question. An image is billed on every use: on 2026-10-19 the input tokens of a W×H image fit 2·⌈W/28⌉·⌈H/28⌉, plus about 4 per use — an observation, not a published rate.

r = ask("Help! My payouts have been failing for 3 days.",
        "urgency" => score("How urgent is this ticket?",
                           ["Can wait", "Needs attention this week", "Needs attention today"]))

println(answer(r, "urgency"))
u = token_usage(r)                     # prompt_tokens = input, completion_tokens = output
println(u.prompt_tokens, " billable tokens")
println("USD ", estimated_cost(r))     # priced against r.response.model

estimated_cost prices the versioned id in r.response.model, not the alias the request named: a jev-X.Y.Z id without its own row at the jev-latest row, and any other name that is not a key in DEFAULT_PRICING at 0.0 (Cost Tracking).

OpenAI Decisions

OpenAI's Decisions API (POST /v1/decisions, a public beta from October 6, 2026, now generally available) answers predicate, choice and score questions, and OPENAIServiceEndpoint speaks it: name the endpoint as the service of ask or of a with_system_one scope, and set OPENAI_API_KEY. The model is gpt-6-luna, the only one the API serves, unless the call names another (Decisions guide).

r = ask("Export fails in Safari but works in Chrome.",
        "severity" => score("How severe is this issue?",
                            ["Cosmetic", "Workaround available", "Fully blocked"]),
        "angry"    => noul("Is the customer angry?");
        service = OPENAIServiceEndpoint)

with_system_one(OPENAIServiceEndpoint) do
    nl_classify(ticket, INTENT)          # every verb inside asks OpenAI
end

Every question needs string instructions, and at most 400 go in one request. prompt_cache_options takes a ttl of "30m" or "12h" — OpenAI's prompt-caching guide names "12h" for the Responses API, and the Decisions API answered a "12h" request with HTTP 200 — and a mode; with mode="explicit" the request marks no breakpoint, so OpenAI caches none of it. What has no form on this wire — a Box question, a description or level that is not a string, a Noul's yes/no criteria, an image outside the state, another ttl, prewarm or comparison_response_id, any other keyword — is an ArgumentError before anything is sent. The answers come back typed as on any backend, and a question the API declined comes back as a RefusalAnswer: nl_dispatch, nl_classify and @branch take it as a decline — the fallback, or DecisionDeclinedError. Probabilities and confidences arrive rounded to two decimals, so a distribution over n outcomes is accepted when it sums to 1 within 0.005n, and the chosen option when it lies at most 0.01 below the most probable. usage counts input, cached, cache-write (the 12-hour ones apart) and output tokens, and holds the service tier when the reply names one; a count that is not a non-negative whole number, or a …_tokens_details value that is not an object, reads as 0 with a warning. A failure's error_type is the error's code, and the request id is the x-request-id header. A recording (with_recorded_answers) is keyed without the three options, and holds each image as the SHA-256 of its base64 text, data:<mime>;sha256,<hex>, never its bytes. estimated_cost charges what the guide prices: input tokens only — $0.10 per million uncached, the gpt-6-luna row's input rate; cache reads at its cached rate, $0.01, and cache writes at OpenAI's write rates, $0.125 per million ($0.25 for a 12-hour lifetime) — every rate twice for a request of more than 272K input tokens.

The calls are bounded as TypeSafe's are (60 s per attempt, 150 s in all, while you set no RequestConfig of your own), and ask_each keeps 16 of them in flight. list_models on this endpoint lists every model OpenAI serves the key (Model Listings). On the 129 support tickets of the Backends section, OpenAI answered in 0.48 s at the median and 2.44 s at the 95th percentile (Jev: 0.25 s and 0.33 s), at $0.0000296 a ticket (Jev: $0.0000225).

OpenAIDecisionsProtocol <: SystemOneProtocol

OpenAI's Decisions API, generally available, as a System One backend, and the protocol of OPENAIServiceEndpoint: ask(state, questions...; service = OPENAIServiceEndpoint), a with_system_one(OPENAIServiceEndpoint) scope and the natural-language verbs send POST https://api.openai.com/v1/decisions with OPENAI_API_KEY, naming "gpt-6-luna" — the only model the API serves — when the call names none.

The request:

  • state is the input: a string as it is; a JSON value (object, array, tuple, NamedTuple) as its JSON text; an ImageAttachment, or a vector or tuple of strings and images, as one user message of input_text and input_image parts (base64 data URLs, each with its detail when the image sets one), in order. Images go there and nowhere else, at most 128 of them; each text — the input, or each text part of the message — is at most 10,485,760 characters.
  • each question is one entry of questions, in order, carrying its name: a NoulQuestion a predicate; a ChoiceQuestion a choice of 2 to 255 options, each option's name its value and a string description its description (none for nothing); a ScoreQuestion a score of 2 to 10 levels, each level its label; a RawQuestion verbatim, with its name added as "name" when it has none. At most 400 questions; each question's name, instructions, option names and descriptions and level labels, and the model's name, at most 1,048,576 characters.
  • provider options are keywords of ask: prompt_cache_key, a String of at most 64 characters; safety_identifier, at most 128; and prompt_cache_options, a PromptCacheOptions of mode and ttl, "30m" or "12h" (OpenAI's prompt-caching guide names "12h" for the Responses API; the Decisions API answered it with HTTP 200). With mode="explicit" the request marks no cache breakpoint, so OpenAI caches none of it.

What the wire has no form for is an ArgumentError before any I/O, naming OpenAI's rule and the fix: a question without string instructions; a Noul's yes/no criteria; a description or level that is not a string; a BoxQuestion; an image outside the state; a DocumentAttachment anywhere (the API takes no files), as on every System One backend; a prompt_cache_options with another ttl, prewarm or comparison_response_id; any other option.

The reply: answers are matched to the questions by name and must come in the order asked. A predicate reads as a NoulAnswer, a choice as a ChoiceAnswer, a score as a ScoreAnswer whose legend maps each level to its label, and a refusal — the API may decline any question — as a RefusalAnswer. Probabilities and confidences arrive rounded to two decimals, so a distribution over n outcomes may sum to 1 within 0.005n. usage counts input, cached, cache-write — the 12-hour ones apart, as on the Responses API — and output tokens, and holds the service tier when the reply names one; request_id is the x-request-id header; a reply with a status other than 200 is a SystemOneFailure whose error_type is the error's code, else its type. Recordings are filed under /openai-decisions/v1/decisions, keyed without the three options, which change how a request is served but never what it is answered, and with each image as the SHA-256 of its base64 text, never its bytes. estimated_cost bills what OpenAI bills: the input tokens alone, and no output — uncached ones at the model's input rate, cache reads at its cached-input rate, and cache writes and a request of more than 272K input tokens at the surcharges OpenAI lists for the model (gpt-6-luna: a write at 1.25 times the input rate, 2.5 times for a 12-hour lifetime, and every rate twice above 272K).

Ollama

An OllamaEndpoint answers System One requests from a local decision model — Tev1, Nimble, Kev, Clef and the others Ollama lists as decision models — through Ollama's TypeSafe-compatible route POST /v1/systemone: Ollama 0.35 or later, 0.35.1 or later for pictures, and 0.40.0 or later for the MLX builds of Tev1 and Clef Flash used below; what this section reports was measured on 0.40.6. The verbs, the questions and the result types are the ones below; no key is sent and nothing is billed. Start the server and pull the decision models first: the example below uses tev1:4b, clef-flash:9b (a vision model, for pictures) and kev:0.8b-q8_0 (ollama pull tev1:4b, and so on).

ollama = OllamaEndpoint()                     # OLLAMA_HOST, else http://127.0.0.1:11434

r = ask("Help! My payouts have been failing for 3 days.",
        "department" => choice("Which team should handle this ticket?",
                               (billing = "Payments, invoicing, payouts, refunds",
                                technical = "Bugs, outages, integrations")),
        "is_frustrated" => noul("Is the customer frustrated?");
        service = ollama, model = "tev1:4b")

photo = ImageAttachment("parcel.jpg")         # a vision decision model sees the state's images
ask([photo, "A photo sent in with a return."], "damaged" => noul("Is the item damaged?");
    service = ollama, model = "clef-flash:9b")

INTENT = (refund = "the customer wants a refund", bug = "the customer reports a software bug")
with_system_one(ollama; model = "kev:0.8b-q8_0") do     # every verb inside asks Kev
    nl_classify("I was charged twice. Please give me my money back.", INTENT)   # :refund
end
  • Model. There is no default: name an installed decision model with model = …, or set one for a scope with with_system_one; a call without one is an ArgumentError before anything is sent. A model that is not installed comes back as a 404 SystemOneFailure whose message says to ollama pull it, and a server that does not answer as a SystemOneCallError that says how to start one.
  • Refused before any request. ask throws an ArgumentError naming Ollama, the rule and the fix for what Ollama's route refuses in its shared checks or documents as its maximum (Ollama 0.40.6): more than 64 questions; a Choice of more than 255 options; a Score of fewer than 2 or more than 10 levels; a blank text state without images; a Box question, which Ollama does not answer. By Ollama's source, a Kev model on Ollama's own runner (such as kev:0.8b-mxfp8) skips the shared checks and takes 1 to 255 levels and a blank state; that is untested. It also refuses what Ollama's API reference does not list, though some models read it: instructions given as anything but a string, an object or an array; an option described by anything but a string or nothing; a Score level or a Noul criterion that is not a string (on Ollama 0.40.6, kev:0.8b-q8_0 and d1:3b, on the llama.cpp path, answered an option described by an object, and tev1:0.8b refused it). It refuses blank (whitespace-only) instructions, which Ollama would read as none: not blank, as the reference's pattern: \S requires; a Choice, Noul or Score question without instructions, which the API reference requires; and a Choice of one option, below the two it requires.

Questions

UniLM.SystemOneQuestionType#
SystemOneQuestion

Abstract supertype of the questions a System One request asks: ChoiceQuestion (pick one of the named options), ScoreQuestion (place the state on an ordered rubric), NoulQuestion (the probability that a statement is true), BoxQuestion (where something is in an image), and RawQuestion, the hatch for a question kind this version does not know. Build them with choice, score, noul and box.

The types hold only what every backend requires; how many options or levels a backend accepts is its wrapper's rule, checked when the request is sent.

UniLM.choiceFunction#
choice(instructions, criteria) -> ChoiceQuestion
choice(criteria) -> ChoiceQuestion

Build a Choice question: the model picks exactly one of the named options and reports a probability for every one of them.

criteria may be a NamedTuple, an AbstractDict, a vector of name => description pairs, or a vector of bare option names (each described by its name alone). Names may be Strings or Symbols and are stored as Strings; a description may be a string, an object, an array, an image, or nothing.

Option order is the order of what you pass: a NamedTuple, a vector of pairs, and an ordered mapping such as JSON.Object keep theirs. A plain Dict has none of its own — its hash order changes between Julia versions — so its options are taken in sorted name order. Order never changes the answer's meaning — answers are keyed by name — but it is what the model reads.

How many options a question may offer is the backend's rule, checked when the request is sent: TypeSafe accepts up to 255.

choice("Which team should handle this ticket?", (
    billing   = "Payments, invoicing, payouts, refunds",
    technical = "Bugs, outages, integrations",
    sales     = "Pricing, upgrades, new accounts",
))

choice(["billing", "shipping", "other"])   # descriptions are the names themselves
UniLM.scoreFunction#
score(instructions, levels::AbstractVector) -> ScoreQuestion
score(levels::AbstractVector) -> ScoreQuestion

Build a Score question over an ordered rubric, lowest level first. levels[1] is level 0: the answer's score and its probabilities keys live on that same 0-based scale.

Each level is a string, an object, an array or an image — never nothing. How many levels a rubric may have is the backend's rule, checked when the request is sent: TypeSafe accepts 1 to 10 and advises at least two, since a one-level rubric gives the model nothing to place the state against.

score("How urgent is this ticket?",
      ["Can wait", "Needs attention this week", "Needs attention today"])

levels is a vector: a tuple, or any other container, throws ArgumentError, as a choice criteria outside its forms does.

The returned score is a probability-weighted expectation, so it falls between integer levels. Threshold it; do not read a magnitude into the fractional part.

UniLM.noulFunction#
noul(instructions; yes=nothing, no=nothing) -> NoulQuestion
noul(; yes=nothing, no=nothing) -> NoulQuestion

Build a Noul question — a single probability that the statement is true. yes and no describe the two sides and are sent as the wire keys "true" and "false"; either may be omitted.

At least one of instructions, yes, or no must be present: a bare noul says nothing about what is being asked.

noul("Is the customer frustrated?";
     yes = "The customer expresses frustration or impatience",
     no  = "The customer is neutral or satisfied")

A Noul answer carries no confidence — the probability itself expresses it — and P(q) + P(not q) is not guaranteed to be 1, so do not derive one from the other.

UniLM.boxFunction#
box(instructions) -> BoxQuestion

Build a Box question: where in an image of the state is what instructions names. The answer is a BoxAnswer — a BoxCoordinates of fractions of the image's height and width, with a confidence when the backend reports one. instructions is required: a string that is not blank, an object, an array or an image.

box("the dent on the front bumper")
UniLM.ChoiceQuestionType#
ChoiceQuestion(instructions, criteria::JSON.Object{String,Any})

One question that picks a single named option. criteria maps each option name to its description, in insertion order (the order is sent on the wire; the answer's probabilities map is unordered). A description of nothing tells the model to interpret the option by its name alone.

Constructed through choice, which normalizes the many ways to spell a criteria map. At least one option is required and option names must not be blank; there is no upper bound here, because backends differ — TypeSafe accepts at most 255 options, a limit its wrapper checks before the request is sent.

UniLM.ScoreQuestionType#
ScoreQuestion(instructions, criteria::Vector{Any})

One question that places the state on an ordered rubric. criteria lists the levels lowest first; criteria[1] is level 0 on the 0-based scale the answer reports, so a rubric of three levels yields a score in 0.0 … 2.0.

Constructed through score. At least one level is required and a level may not be nothing: an unnamed level is a rung the model cannot recognise. There is no upper bound here — TypeSafe accepts at most 10 levels, a limit its wrapper checks before the request is sent.

UniLM.NoulQuestionType#
NoulQuestion(instructions, criteria)

One question answered by a single probability in 0 … 1 — the model's belief that the statement holds. There is no confidence and no distribution: the value is the distribution, and 0.5 is maximal uncertainty.

Constructed through noul. A noul carrying neither instructions nor a criterion asks nothing, so that is an ArgumentError.

UniLM.NoulCriteriaType#
NoulCriteria(yes, no)

The two optional criteria of a NoulQuestion: what makes the statement true (yes, sent as the wire key "true") and what makes it false (no, sent as "false"). Either may be nothing, in which case that key is omitted entirely rather than sent as null.

UniLM.BoxQuestionType#
BoxQuestion(instructions)

One question that locates something in an image of the state: the answer is a BoxAnswer, a box whose edges are fractions of the image's height and width. instructions says what to locate and is required — a string that is not blank, an object, an array or an image; a box with no target is not a question.

Constructed through box. Not every backend answers Box questions; those that cannot refuse the request with an ArgumentError before it is sent.

UniLM.RawQuestionType#
RawQuestion(fields::AbstractDict)

A question of a kind this version has no type for, kept as the JSON object fields and sent verbatim by the backends that allow raw questions — TypeSafe, OpenAI's Decisions API (which adds the question's name as "name") and Ollama all do; a backend that does not refuses it before the request is sent. fields is copied into a JSON.Object{String,Any} with String keys — a plain Dict in sorted key order, any other dictionary in its own order — and must hold a non-blank String "type".

Its answer is accepted whatever kind it is: an answer the decoder recognises comes back typed, any other as an UnknownAnswer.

r = ask(state, "rank" => RawQuestion(JSON.Object("type" => "rank", "items" => ["a", "b"])))

Request & Verbs

UniLM.SystemOneRequestType#
SystemOneRequest(state, questions; model=nothing, options=(;))

One System One evaluation: every question in questions is answered about the same state, in a single round trip. The state is ingested once no matter how many questions ride along, which is why batching is far cheaper than one call per question.

Fields

  • state::SystemOneState: a string, object, array or image — the content every question refers to. A question points into it by naming a key in backticks, e.g. "Does `refund_policy` cover this charge?".
  • questions::Vector{Pair{String,SystemOneQuestion}}: ordered, with unique names that are not blank. Answers come back keyed by these names.
  • model::Union{Nothing,String}: the model to ask, such as "jev-latest" or a pinned "jev-1.13.0" on TypeSafe; nothing leaves it to the backend that sends the request and is resolved only then — to the model of the enclosing with_system_one scope when the call names no service, otherwise to the backend's default (TypeSafe: UniLM.default_typesafe_model(), read at send time). Aliases move; pin the version if you have tuned thresholds against it, and read SystemOneResponse.model to see which version answered.
  • options::NamedTuple: provider options, checked by the backend's wrapper when the request is sent; keyword arguments of ask become these. TypeSafe accepts one, long_context::Bool; OpenAI's Decisions API prompt_cache_key, safety_identifier and prompt_cache_options; Ollama keep_alive.

questions accepts name => question pairs (vector, tuple, NamedTuple, or AbstractDict), or bare questions in a vector or tuple, which are auto-named "q1", "q2", … in order; a plain Dict of questions is taken in sorted name order. A state of any other type, mixing bare and named questions, repeating a name, a blank name, passing none, or passing a blank model is an ArgumentError.

UniLM.askFunction#
ask(request::SystemOneRequest; service=nothing, config=nothing, cancel=nothing)
ask(state, questions...; model=nothing, service=nothing, config=nothing, cancel=nothing, options...)

Evaluate every question against state in one request to a System One backend and return one of SystemOneSuccess, SystemOneFailure (a response with a status other than 200) or SystemOneCallError (no response, or a 200 that was not a usable set of answers). Inside a with_recorded_answers scope, a request the scope cannot replay — no recording in :replay mode, or a recording file that cannot be read — throws ReplayMissError instead of returning: a gap in the recordings is not a service failure.

The backend is service when given, else the one of the enclosing with_system_one scope, else TYPESAFEServiceEndpoint. The model is model (or the request's) when given; else, with no service, the scope's; else the backend's default, read when the request is sent (TypeSafe: TYPESAFE_DEFAULT_MODEL, or "jev-latest").

questions takes the same forms as SystemOneRequest: name => question pairs, a NamedTuple or AbstractDict of them, or bare questions auto-named "q1", "q2", … Any other keyword is a provider option and becomes the request's options, which the backend's wrapper checks before anything is sent: TypeSafe accepts long_context::Bool (true raises its context limits to 262k tokens), OpenAI's Decisions API prompt_cache_key and safety_identifier (strings) and prompt_cache_options (a PromptCacheOptions), Ollama keep_alive (the seconds the model stays loaded), so any other keyword — a misspelt one included — is an ArgumentError that lists the options the backend accepts.

r = ask("Help! My payouts have been failing for 3 days.",
        "department" => choice("Which team should handle this ticket?",
                               (billing="Payments, invoicing, payouts, refunds",
                                technical="Bugs, outages, integrations",
                                sales="Pricing, upgrades, new accounts")),
        "urgency" => score("How urgent is this ticket?",
                           ["Can wait", "Needs attention this week", "Needs attention today"]))
issuccess(r) && println(r["department"].choice, " ", r["urgency"].score)

Malformed input is an ArgumentError before anything is sent: a state that is not a string, object, array or image; a value JSON cannot carry (NaN, Inf); a request the backend cannot carry — TypeSafe takes at most 255 options per Choice and 10 levels per Score, PNG and JPEG images of at most 16 MiB with 280 to 1568 pixels on each side (a JPEG ending with its end-of-image marker), 64 levels of nesting in the state, instructions and criteria, and a body of at most 32 MiB; a service that does not declare :system_one.

Every answer is checked against the request before a success is built: each question asked is answered once and nothing else is; each answer is of its question's kind (an answer to a RawQuestion may be any); a Choice picks an offered option that is the most probable and gives a probability to exactly the options offered; a Score gives one to exactly the levels 0 to n − 1, its score lies between them and is the expectation of its probabilities within the backend's rounding, and its legend repeats every level asked as a string; probabilities lie in 0 … 1 and sum to 1 within the backend's rounding; confidences, Noul probabilities and box edges lie in 0 … 1; the response names the model that answered, by a name that is not blank. A reply that fails any of these is a SystemOneCallError — never a success built from a malformed answer.

Pass config::Union{Nothing,RequestConfig} to override the timeout and retry budget for this call. With none — no config, no with_request_config scope, no process default set — the backend's own default applies: on TypeSafe and OpenAI's Decisions API, 60 s per attempt and 150 s in all. On TypeSafe a retry carries its number in X-TypeSafe-Retry-Count, as the official SDKs send it. The request rides the package's shared retry seam, so max_attempts applies: a retryable status (408, 429, 500, 502–504, 520–524, 529) or a transport failure is retried within total_deadline, honouring retry-after-ms, else Retry-After. Other statuses — 400, 401, 403, 404, 413, 415, 422 — are returned as they came, because a second identical request cannot fix them.

Pass cancel::Union{Nothing,CancelToken} (default: the ambient with_cancel token) to make the call cancellable: once the token is cancelled it returns a SystemOneCallError whose cause is a UniLMCancelled — without sending anything when the token was already cancelled, at once when mid-request (never retried).

UniLM.ask_eachFunction#
ask_each(states::AbstractVector, questions...; model=nothing, service=nothing, config=nothing,
         cancel=nothing, ntasks=nothing, on_result=nothing, options...)
ask_each(requests::AbstractVector{<:SystemOneRequest}; service=nothing, config=nothing,
         cancel=nothing, ntasks=nothing, on_result=nothing)

Ask the same questions about every state — or send every request — concurrently, and return a Vector{Union{SystemOneSuccess,SystemOneFailure,SystemOneCallError}} whose i-th entry is the result for item i: what ask returns for that item alone, with the same answers. Each item is a request of its own; nothing is packed together.

questions, model, service, config and any other keyword — a provider option — mean what they mean for ask, and the backend and model resolve as they do there, an enclosing with_system_one scope included. Every request is built and checked by its backend's wrapper before the first one is sent: an item that cannot be sent is an ArgumentError naming its position, and nothing is sent. The checked request is not kept: the worker that sends an item encodes it again, so a batch holds no more request bodies — images and all — than it has requests in flight.

At most ntasks requests are in flight at once — any Integer of at least 1; the default is the backend's — 16 on TypeSafe's wire (a TypeSafe-compatible gateway included) and OpenAI's Decisions API, 1 on Ollama, 8 on a protocol of your own — a default, not a limit. The requests share one connection pool, and when the service answers any of them with 429 or 529, a retried attempt included, no attempt of the batch starts until the wait that response asked for (retry-after-ms, else Retry-After, else the retry seam's own backoff) has passed; requests already in flight finish. A request waits at most what remains of its own total_deadline, whose clock starts when a worker takes it: one whose budget runs out while it waits is not sent, and its result is a SystemOneCallError whose cause is a UniLMTimeout of phase :deadline.

on_result(i, result), when given — any callable of an index and each kind of result, checked before anything is sent — runs in the worker task as each result lands, in the order they complete, one call at a time.

cancel (default: the ambient with_cancel token) stops the batch: the requests in flight end at once, the rest are not sent, and each item still unanswered becomes a SystemOneCallError whose cause is a UniLMCancelled, as for ask. A ReplayMissError or RecordingWriteError inside with_recorded_answers, an InterruptException, or an exception thrown by on_result stops it as well and is rethrown — the first one — once every worker has stopped.

tickets = ["My order arrived broken, I want a refund.", "The app crashes when I log in.",
           "Do you ship to Canada?"]
results = ask_each(tickets, "team" => choice(["billing", "technical", "shipping"]))
[issuccess(r) ? r["team"].choice : nothing for r in results]
UniLM.with_system_oneFunction#
with_system_one(f, service; model=nothing, options...)

Run f() with service as the System One backend of every verb inside it that names none — ask, list_models, nl_dispatch, nl_classify and @branch — model, when given, as the model of those calls that name none, and any other keyword as the provider options of those calls that name none (see ask; checked by the backend's wrapper when each request is sent); return f()'s value. service must declare :system_one and model must not be blank, or this is an ArgumentError before f runs.

A call resolves its backend, model and options this way:

  • with service: that backend, and model and options if the call names them, else the backend's default model and no options — the scope's model and options belong to the scope's backend and are never applied to another;
  • without service: the scope's backend, and the call's model if it names one, else the scope's; the call's options if it names any, else the scope's;
  • outside every scope: TYPESAFEServiceEndpoint and its default model.

The scope is a ScopedValue, so it covers the tasks started inside f (Threads.@spawn, asyncmap), and scopes nest: the innermost applies.

with_system_one(TYPESAFEServiceEndpoint; model = "jev-1.13.0", long_context = true) do
    nl_classify(ticket, INTENT)          # asks jev-1.13.0, with TypeSafe's long context
end

Answers

UniLM.SystemOneAnswerType#
SystemOneAnswer

Abstract supertype of the answers a System One evaluation returns: ChoiceAnswer, ScoreAnswer, NoulAnswer, BoxAnswer, RefusalAnswer when a backend declined one question, and UnknownAnswer for a type this version does not recognise.

UniLM.ChoiceAnswerType#
ChoiceAnswer(choice, confidence, probabilities, raw)

The option with the highest probability (choice), a confidence in 0 … 1 summarising how concentrated the distribution is, and probabilities — one entry per option of the question, keyed by option name and summing to 1 within the backend's rounding. The map is unordered: a backend need not return the request's option order.

Read probabilities when the ranking matters; choice is only its argmax. raw is the unparsed JSON answer.

UniLM.ScoreAnswerType#
ScoreAnswer(score, confidence, legend, probabilities, raw)

score is the probability-weighted expectation over the rubric levels, so it may fall between them; confidence is in 0 … 1. legend and probabilities are keyed by the 0-based level number (parsed from the wire's "0", "1", …), so argmax(a.probabilities) is a level on the same scale as score and legend[argmax(a.probabilities)] is that level's description — a string, the original object/array when the rubric was structured, or the level's own ImageAttachment when it was an image.

raw is the unparsed JSON answer.

UniLM.NoulAnswerType#
NoulAnswer(noul, raw)

Provider protocol

Every System One verb reaches its backend through a protocol, a Holy trait of the endpoint: system_one_protocol maps an endpoint to a SystemOneProtocol, whose encode_system_one turns a request into a SystemOneWire — what is sent, and the record_body a recording is keyed on and writes; refusing, before any I/O, what its backend cannot carry — and whose decode_system_one turns the reply into a typed result, its answers checked against the request. The rest is shared by every backend: the backend and model a call resolves (through with_system_one), recording and replay, retries and cancellation, the connection pool, and credentials, which auth_header supplies only when a request really goes out, so a replay needs no key. Three protocols ship: TypeSafeProtocol above, and OpenAIDecisionsProtocol and OllamaSystemOneProtocol in their backends' sections.

An endpoint that declares :system_one and no protocol of its own speaks TypeSafeProtocol, TypeSafe's wire — a TypeSafe-compatible gateway or proxy needs no protocol code (Service Endpoints shows one). A protocol other than TypeSafe's files its recordings under a namespace of its own, before the request's path (/ollama/v1/systemone), so two backends never replay each other's answers, while every TypeSafe recording keeps its key.

UniLM.SystemOneProtocolType#
SystemOneProtocol

Abstract supertype of the System One wire protocols, the trait value system_one_protocol returns for an endpoint. A protocol is a singleton type; its methods of encode_system_one and decode_system_one are the whole of a backend's wire. TypeSafeProtocol is the first.

UniLM.TypeSafeProtocolType#
TypeSafeProtocol <: SystemOneProtocol

TypeSafe's System One wire: POST {base}/v1/systemone with the JSON body {"state", "model", "questions"} in the System One JSON form, answers decoded from {"model", "answers", "usage"}, the request id read from the x-typesafe-request-id header, and failures from TypeSafe's three error-body shapes. Recordings are keyed under the plain path (no namespace). It sends a RawQuestion verbatim and never expects a refusal.

TypeSafe marks images and Box questions "Dreamer-ready": they "aren't yet up to our standards to call ready for production", and their request format, answers and limits "can change between releases" (Images). Each distinct ImageAttachment of a request — in the state, an instruction, a criterion or a raw question's fields — is sent once, as a part of a multipart/form-data request whose first part, request, holds the JSON body; every place the image stood holds its reference, "<image:…>" with the first 32 hex digits of the SHA-256 of its bytes, and the body lists the parts under assets. A request with an image or a BoxQuestion carries the header TypeSafe-Danger-Zone-Images: true: passing one is the opt-in. A Score level that is an image comes back in the answer's legend as that ImageAttachment. The one provider option, long_context = true, sends TypeSafe-Danger-Zone-Long-Context: true, which raises the context limits from 64k tokens per request and 32k per question to 262k at the same price per token.

Before any I/O it refuses what TypeSafe rejects: more than 255 options in a Choice or 10 levels in a Score; an image that is not a still PNG or JPEG, is over 16 MiB, has a side under 280 or over 1568 pixels, whose header cannot be read, or a JPEG that does not end with its end-of-image marker; more than 64 levels of nested objects and arrays in the state, an instruction or a criterion; a body over 32 MiB; a DocumentAttachment anywhere, as on every System One backend; an image's detail level, for which an image asset has no field; and any option but long_context. Two terse failures get a hint in their message: a context overflow (error_type = "max_tokens_exceeded") names long_context and the limits, and the "Invalid request." a Box question draws from a Jev before 1.14 names the models that answer one.

The untyped fallback of system_one_protocol returns it, so TYPESAFEServiceEndpoint and every endpoint that declares :system_one without a protocol of its own speak it.

UniLM.SystemOneWireType#
SystemOneWire(method, url, path, body, parts, headers, key_extra[, record_body])
SystemOneWire(method, url, path, body; parts=[], headers=[], key_extra="", record_body=body)

One System One exchange as a protocol encoded it — what is sent and what its recording is keyed by. Credentials are not part of it: the endpoint's auth_header is read only when the request really goes out, so a replay needs no key.

Fields

  • method::String, url::String: the request line, sent as is.
  • path::String: the path the recording key uses — never derived from url, so no host, proxy prefix or query ever moves a key. Must start with / and hold no ? or #.
  • body::String: the JSON body exactly as sent (the request part when the exchange is multipart).
  • parts::Vector{Pair{String,ImageAttachment}}: images sent as parts after the body. Empty: the body is sent as it is. Not empty: the request is multipart/form-data — first a part named request (application/json, no filename) holding body, then one part per name => image, in order, whose filename is its name and whose content type is the image's.   • headers::Vector{Pair{String,String}}: extra headers that are not credentials, such as a feature gate; sent after the endpoint's auth_header.
  • key_extra::String: appended to what the recording key is computed over, after a newline, when it is not empty — the canonical form of the request's options, digests of its parts — so requests that differ only there are recorded apart.
  • record_body::String: the body as a recording is keyed on and writes it — body itself unless the protocol leaves out fields that change how a request is served but never what it is answered (Ollama's keep_alive; OpenAI's prompt_cache_key, safety_identifier and prompt_cache_options), so requests that differ only there replay one recording. What is sent is body.

Recorded answers

A service does not answer a repeated request identically, so a test or a docs build that calls it live cannot be reproduced. with_recorded_answers records a real answer once and replays it offline. Inside its scope, ask and TypeSafe's list_models (and so nl_dispatch, nl_classify and @branch), chatrequest! and respond, streamed or not, and embeddingrequest! (and so the tool loops), the Responses lifecycle calls, fim_complete and prefix_complete exchange through a directory of recordings keyed by the exact request bytes — with any credential the body carries redacted, every base64 data: URL it carries (an image, a PDF, audio, any media) replaced by the SHA-256 of its base64 text, and a System One backend's options that change how a request is served left out (media sent as bare base64 are written as sent, such as Ollama's chat images or an input_audio clip, except the images of an Ollama System One request and the media of an Ollama embeddings request, keyed and written by digest too); images, audio, files, MCP and every other verb reach the network as usual. In the default :replay mode no recorded verb reaches the network and none needs a key, and a request with no recording, or an unreadable one, throws ReplayMissError; :record and :record_missing call the service — with its key, or its local server running — for the answers they write. A build of this documentation without a recording flag replays every such example, System One and LLM alike.

UniLM.with_recorded_answersFunction#
with_recorded_answers(f, dir::AbstractString; mode::Symbol = :replay)

Run f() with the service exchanges inside it passing through the recordings in dir, and return f()'s value. Recorded: ask (and so nl_dispatch, nl_classify and @branch), TypeSafe's list_models, chatrequest! (with its keyword form and tool_loop!) and respond (with its convenience forms and tool_loop), streamed or not, embeddingrequest!, the Responses lifecycle calls (get_response, delete_response, list_input_items, cancel_response, compact_response, count_input_tokens), fim_complete and prefix_complete. Everything else reaches the network as usual — images, audio, files, batch, moderation, the model listings other than TypeSafe's, Ollama's model pulls, realtime, MCP and every other verb behave inside a scope exactly as outside it.

A service does not answer a repeated request identically, so a test or a docs build that calls it live cannot be reproduced; one recorded answer, replayed, can. A request's bytes can depend on the clock: a follow-up that sends an OpenAI audio reply back by its id sends it as text from a minute before the audio's expires_at (AudioOutput), so its recording, made while the audio was live, replays only until then; record such a follow-up after the expiry.

  • :replay (the default): no recorded verb reaches the network or needs an API key; a verb the scope does not record — images, audio, files, MCP, … — behaves exactly as outside the scope. A request with no recording, or with a recording file that cannot be read as one, throws ReplayMissError out of the verb itself (and so out of the tool loops; for a later request of a streamed turn, out of the call's task, as below). dir must exist.
  • :record: every request goes to the service; each HTTP 200 is written to dir (a stream once its reply is whole, as below), replacing an earlier recording of the same request, readable or not, so a request repeated identically — a polling loop's — leaves the last 200 it got, which a :replay scope then gives every repetition. A non-200 result is returned as usual and never recorded.
  • :record_missing: replay what dir holds, and send the rest to the service, recording their 200s. A recording is replayed before any request is sent, so once a request's 200 is recorded an identical request replays it: a polling loop records the first status it gets and gets it back on every later poll. An unreadable recording throws ReplayMissError here too instead of being overwritten: delete the file to record it again.

A recording is written after the service has answered, and billed, so both recording modes create dir if needed and prove it writable — a file is created in it and removed — before f runs: a dir that is a file, or a directory that refuses a file, is an ArgumentError naming the path and the cause, and nothing is sent. A recording that still cannot be written once an answer has arrived — the directory was removed or replaced, the disk is full — throws RecordingWriteError, with that I/O error as its cause, out of the verb (and so out of nl_dispatch, nl_classify, @branch and the tool loops, a dispatcher's own request included) instead of returning its call error: the answer was paid for, and a caller's r isa SystemOneSuccess || fallback() path must not absorb the lost write as a service failure. A streamed call reads its reply inside the task it returns, so its lost write — and a miss on a later request of a turn the provider continues (Gemini 4 Argon's long decode) — is thrown inside that task: fetch, and so tool_loop! on a streamed chat, throws a TaskFailedException whose task.exception is the error. A miss on the first request is thrown by the streamed verb itself. A miss or lost write of a recorded call made in a stream's callback or on_tool_call is thrown inside the stream's task too, as the callback threw it.

A recording is <dir>/<key>.json, where key is the lowercase hex SHA-256 of "<METHOD> <path>\n" followed by the exact request body, and <path> is the path of the request URL alone: never its host, nor its query, which can carry a credential. A System One backend other than TypeSafe files its requests under a namespace of its own, followed by its wire's path — "/openai-decisions/v1/decisions" for OpenAI's Decisions API, "/ollama/v1/systemone" for Ollama — so the same question asked of two backends is two recordings; a System One request that carries an option its backend keys (TypeSafe's long_context) or image parts, and a list_input_items request, whose query names the page, append a newline and their canonical text — options and the page's limit, order and after as sorted name=value lines with JSON values, parts as their names and SHA-256 digests — to the body they are keyed on, so a request without them keeps its key; and a System One backend keys its body without the options that change how a request is served but never what it is answered — Ollama's keep_alive, OpenAI's prompt_cache_key, safety_identifier and prompt_cache_options — which are sent, and neither keyed nor written, so the same question replays one recording whatever they are. The key is never a canonical form of the request: the order of Choice options and of the state's keys moves the answer, so a reordered request is a different request. Two changes are made to the body. A credential it carries: in each object of its top-level tools array, an MCP tool's authorization and headers ("type": "mcp", the OpenAI Responses wire), a Gemini Interactions MCP server's headers ("mcp_server") and the api_key of a Gemini "retrieval" tool's exa_ai_search_config and parallel_ai_search_config read "<redacted>" in the key, the file and a ReplayMissError, so a replay needs none of them; the request sent carries them as given. And every base64 data: URL it carries — an image, a PDF, audio, any media: an OpenAI chat attachment, an OpenAI Decisions image, a Responses input_image or input_file — reads data:<mime>;sha256,<hex>, the SHA-256 of that base64 text, in the key, the file and a ReplayMissError: a recording names the media it answered without holding their bytes, and other media is another request. The file holds the request (with that canonical text as key_extra when there is one), the response body — for a streamed request, the lines of the streamed body (stream) — with its request id, the name of the header that carried it (x-typesafe-request-id, x-request-id or request-id) and the headers a replay gives back (headers: the request-id headers and x-gemini-service-tier, the tier Gemini billed the reply at, those the reply carried), and the time of recording, pretty-printed so a diff is readable; the API key, every other header, an MCP tool's authorization and headers, and the bytes of media sent as a base64 data: URL or as a System One image part are never written. Media sent as bare base64 is written as sent — Ollama's chat images, an input_audio clip — except the images and sound clips of an Embeddings request to an OllamaEndpoint and the images of a System One request to one: they are keyed and written as their digests, data:<mime>;sha256,<hex>, as the same media sent as a data URL would be. A replay gives back the headers its recording kept; a recording made before they were kept gives back its request id alone, under the header it names (x-typesafe-request-id when it names none). Files are written atomically (a temporary file in dir, then a rename), so concurrent tasks can record at once. A replayed answer goes through the same decoding as a live 200 and has the same type and fields: a Chat gets the reply appended and its cost accumulated, and Embeddings get their vectors. A replayed stream is read through the same parsers and callbacks as a live one, with no first-byte deadline or idle guard; a stream is recorded only when its reply is whole — its final event arrived: the sentinel ([DONE], Anthropic's message_stop, Ollama's done), the end of a native Gemini stream, or a Responses or Interactions terminal event — and was read with no stop, also when its connection fails after that event. A stream that ends with an error event, or is cut before its final event, is not recorded, even when the call keeps the turn its finish reason completed. A cancelled token ends a call before any recording is read, exactly as it ends one before anything is sent.

The scope is a ScopedValue, so it covers the tasks started inside f (Threads.@spawn, asyncmap). Scopes nest: an inner scope's service is the enclosing scope, so a :record scope inside a :replay scope copies the replayed answers without touching the network. A mode other than the three above is an ArgumentError, as is :replay with a dir that does not exist.

const ANSWERS = joinpath(@__DIR__, "recorded_answers")

with_recorded_answers(ANSWERS) do          # replay: no key, no network
    r = ask("My payouts have been failing for 3 days.",
            "urgency" => score("How urgent is this ticket?",
                               ["Can wait", "Needs attention this week", "Needs attention today"]))
    r["urgency"].score                     # the recorded answer, every run
end

A request that has no recording yet is recorded by running the same code once with access to its service (TYPESAFE_API_KEY for Jev, OPENAI_API_KEY for OpenAI's Decisions API, a running server for Ollama) and mode = :record_missing.

UniLM.ReplayMissErrorType#
ReplayMissError <: Exception

Thrown inside a with_recorded_answers scope when a request cannot be replayed — in :replay mode the directory holds no recording of it, or in :replay or :record_missing mode its recording file cannot be read as one — by the verbs the scope records: ask and TypeSafe's list_models (and so nl_dispatch, nl_classify and @branch), chatrequest! and respond, streamed or not, and embeddingrequest! (and so tool_loop! and tool_loop), the Responses lifecycle calls (get_response, delete_response, list_input_items, cancel_response, compact_response, count_input_tokens), fim_complete and prefix_complete. A verb the scope does not record — images, audio, files, MCP, … — never throws it: it behaves exactly as outside the scope. A streamed call throws it for its first request before returning its task; a miss on a later request of the turn (a reply the provider continues) is thrown inside that task, so fetch — and tool_loop! on a streamed chat — throws a TaskFailedException whose task.exception is it, as it does for a miss of a call made in the stream's callback (task.exception is then what the callback threw). It is thrown rather than returned as the verb's call error (SystemOneCallError, LLMCallError, ResponseCallError, EmbeddingCallError, FIMCallError): a gap in the recordings is not a service failure, and a caller's r isa SystemOneSuccess || fallback() path must not absorb it as if it were one.

Fields

  • dir::String: the recordings directory that was searched.
  • key::String: the recording key; the recording is the file <dir>/<key>.json.
  • method::String, path::String: the request line as keyed, e.g. "POST" and "/v1/systemone" or "/v1/chat/completions": the path of the request URL alone, never its host or query — for a System One backend other than TypeSafe, after the backend's namespace ("/openai-decisions/v1/decisions" for OpenAI's Decisions API, "/ollama/v1/systemone" for Ollama), so backends never share a recording.
  • body::String: what the key was computed over after the request line — the body as its backend keys it, with the credentials with_recorded_answers never writes replaced by "<redacted>" and each base64 data: URL by its digest (empty for a request that sends none, such as GET /v1/models), followed, for a request keyed on more than its body (a System One request's provider options or the digests of its image parts, list_input_items' limit, order and after), by a newline and that canonical text.
  • reason::String: "no recording", or "unreadable recording: …" followed by what is wrong with the file — not JSON, no response object, a status other than 200, a body that is not a JSON object (for a streamed request, a stream that is not an array of strings), a request_id that is neither a string nor null, a request_id_header other than "x-typesafe-request-id", "x-request-id" and "request-id", or a headers that is not an object of string values named among those three and "x-gemini-service-tier".

showerror names the request line, the start of the key, what the request asked for — a System One request's questions, any other request's model when its body names one — the directory or (for an unreadable recording) the file, and how to record the answer: with TYPESAFE_API_KEY set for a TypeSafe request, with access to the provider — its API key, or a local server running — for any other. An unreadable file must be deleted first, because :record_missing never overwrites one.

RecordingWriteError <: Exception

Thrown inside a with_recorded_answers scope in :record or :record_missing mode when the service has answered a request, and billed it, but its recording cannot be written — the directory was removed or replaced after the scope checked it, or the disk is full. The verbs the scope records throw it — ask, TypeSafe's list_models, chatrequest!, respond, embeddingrequest!, the Responses lifecycle calls (get_response, …), fim_complete and prefix_complete — and so do the calls built on them: nl_dispatch, nl_classify, @branch and the tool loops, a request made by a loop's dispatcher included. A streamed call reads its reply inside the task it returns and throws it there, so fetch — and tool_loop! on a streamed chat — throws a TaskFailedException whose task.exception is it; so does a stream whose callback made the call (task.exception is then what the callback threw). It is thrown rather than returned as the verb's call error: the answer was paid for, and a caller's r isa SystemOneSuccess || fallback() path must not absorb the lost write as a service failure. An MCP server tool handler's is answered, like a ReplayMissError, with the generic JSON-RPC -32603 and logged, never relayed to the client.

Fields

  • file::String: the recording that could not be written, <dir>/<key>.json.
  • cause::Exception: what stopped the write, such as a Base.IOError.

showerror names the file and the cause, and says that the answer was billed.
