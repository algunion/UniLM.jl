Azure OpenAI

Azure OpenAI serves the GPT models from an Azure resource of yours, each through a deployment you create. AZUREServiceEndpoint speaks its Chat Completions API in the dated form — a deployment's URL and an api-version — through chatrequest! and tool_loop!. The agentic verbs — respond and the tool_loop that takes an input or a Respond — refuse this endpoint before sending anything, and no verb of a capability the table below lists as not available sends a request through it. Azure's newer v1 API, which takes no api-version, is reachable through a generic endpoint (The v1 API). No key of an Azure resource was at hand for this page: its examples are not run, and their code stands without output.

Setup

Set the resource, its key, the API version and a deployment for each model you call:

export AZURE_OPENAI_BASE_URL="https://your-resource.openai.azure.com"
export AZURE_OPENAI_API_KEY="..."
export AZURE_OPENAI_API_VERSION="2024-10-21"
export AZURE_OPENAI_DEPLOY_NAME_GPT_5_2="your-gpt52-deployment"

UniLM reads these variables each time a request is built, so they may be set after the package loads. A Chat goes to $AZURE_OPENAI_BASE_URL/openai/deployments/<deployment>/chat/completions?api-version=$AZURE_OPENAI_API_VERSION with the key in the api-key header, the form of Azure's dated API versions; 2024-10-21 is the dated GA release Azure's REST reference documents (REST API reference). A field Azure added later needs a later version: reasoning_effort came in 2024-12-01-preview (API versions), and audio replies in 2025-01-01-preview (audio generation). A call without one of the first three variables returns a call-error result whose cause is the KeyError naming it. UniLM sends the key only: Azure's other way in, a Microsoft Entra ID token in an Authorization: Bearer header, is not this endpoint's.

Azure routes a request to a deployment, and UniLM finds the deployment of the model a Chat names. A deployment registered with add_azure_deploy_name! wins; otherwise UniLM reads AZURE_OPENAI_DEPLOY_NAME_<MODEL> when the request is built, where <MODEL> is the model id upper-cased with every character other than A-Z and 0-9 made _ (gpt-5.2 → AZURE_OPENAI_DEPLOY_NAME_GPT_5_2, gpt-6-luna → AZURE_OPENAI_DEPLOY_NAME_GPT_6_LUNA). A model with neither makes the call return an LLMCallError whose cause is an ArgumentError naming the variable to set. The deployment's name is sent as one path segment, percent-encoded. A registration holds for the session, and a second one for the same model replaces it:

add_azure_deploy_name!("gpt-5.2", "my-gpt52-deployment")
chat = Chat(service=AZUREServiceEndpoint, model="gpt-5.2")   # sent to my-gpt52-deployment

A Chat takes the endpoint as the type, service=AZUREServiceEndpoint, and AZUREServiceEndpoint() returns the type too; with no model, it takes the default model named at the top of this page. The model id goes in the request body as well, and it is the id UniLM prices a reply at when Azure's reply names none (Cost and usage).

First call

A Chat starts with its system message; chatrequest! sends it and returns a typed result, and text reads the reply — or throws, on a failure:

chat = Chat(service=AZUREServiceEndpoint)
push!(chat, Message(Val(:system), "You are a concise assistant."))
push!(chat, Message(Val(:user), "In one sentence: what is a prime number?"))
result = chatrequest!(chat)
text(result)
result.model, result.message.finish_reason
u = result.usage
(; u.prompt_tokens, u.completion_tokens, u.reasoning_tokens, u.cached_tokens, cost = estimated_cost(result))

The reply is read as a Chat Completions reply: result.model is the model Azure reports, and finish_reason is Azure's, content_filter "to signify that some of the completion was filtered" (content filtering). prompt_tokens counts the input, of which cached_tokens came from the prompt cache (Prompt caching), and completion_tokens the output, of which reasoning_tokens is the reasoning (Reasoning). The result types are on Results.

Conversations

A Chat keeps the conversation: each reply is appended to it, and the next chatrequest! sends the whole conversation again.

push!(chat, Message(Val(:user), "And a composite number?"))
text(chatrequest!(chat))
[m.role for m in chat.messages], cumulative_cost(chat)

A system message pushed after the conversation started is sent in place. Azure's reasoning models take system messages; "You should not use both a developer message and a system message in the same API request" (reasoning models), and UniLM sends no developer message. What push! refuses is the same on every provider (Chat Completions).

A reply that holds audio (audio_output) goes back to Azure by the audio's id, "audio": {"id": …} beside the turn's transcript, as Azure's quickstart adds "a history message referencing the previous turn's audio by ID" (audio generation), until a minute before the reply's expires_at, and from then on as the transcript alone (Audio replies).

Streaming

With stream=true, chatrequest! returns a Task at once, and fetch gives the same typed result as an unstreamed call; the callback receives the text as it arrives, then the assembled Message. A Chat on this endpoint sends no stream_options unless it sets them, so a streamed turn reports no usage, and adds 0.0 to cumulative_cost, unless the Chat asks for it:

chat = Chat(service=AZUREServiceEndpoint, stream=true, stream_options=Dict("include_usage" => true))
push!(chat, Message(Val(:system), "You are a concise assistant."))
push!(chat, Message(Val(:user), "List the planets of the solar system in order, one per line."))
task = chatrequest!(chat; callback=(chunk, close) -> chunk isa String && print(chunk))
result = fetch(task)
result.usage

Azure added stream_options and include_usage in the API version 2024-09-01-preview (API versions). The stream is the Chat Completions one: a chunk whose choices list is empty, such as the usage chunk, whose "choices field will always be an empty array" (chat REST reference), gives its usage and nothing else; the turn is final at data: [DONE], or, without one, when the HTTP body ends after the finish reason; on_tool_call(tc) runs once per call whose arguments decode, as the next call begins or at the end of the stream; and setting close[] = true stops it (Stopping a Stream Early). The concepts every provider shares are on Streaming.

Tools

Each Tool in tools goes out as a function tool, and tool_choice, parallel_tool_calls and a tool's strict go as they are set; a Chat with tools sends parallel_tool_calls: false unless it sets another value, as Azure asks with strict tools: "Structured outputs are not supported with parallel function calls" (structured outputs). tool_loop! runs the calls and sends their results back until the model answers in text:

weather = UniLM.CallableTool(
    Tool(func=FunctionSignature(name="get_weather", description="Current weather in a city",
        parameters=Dict("type" => "object", "required" => ["city"],
                        "properties" => Dict("city" => Dict("type" => "string"))))),
    (name, args) -> "18°C and sunny in $(args["city"])")
chat = Chat(service=AZUREServiceEndpoint, tools=[weather])
push!(chat, Message(Val(:system), "You are concise."))
push!(chat, Message(Val(:user), "What is the weather in Lyon? Use the tool, then answer in one sentence."))
loop = tool_loop!(chat; tools=[weather])
text(loop.response)

On the GPT-5.6 models, Azure's Chat Completions API refuses function tools at any effort but none: "The gpt-5.6 models support the Chat Completions API and tools, but can't combine reasoning with tools on Chat Completions", and "The request fails even when you don't send reasoning_effort, because these models default to medium"; "If you must stay on Chat Completions, set reasoning_effort to none on every request that sends tools" (reasoning models). UniLM does not check this on Azure: the refusal is Azure's HTTP 400. The loop every provider shares is on Tool Calling.

Structured output

A JSON Schema response_format goes out as {"type": "json_schema", "json_schema": {…}}, with "strict": true when it sets strict, and UniLM.json_object() as {"type": "json_object"}. Azure constrains the reply: "For Chat Completions, define the schema in response_format", and "API version 2024-08-01-preview is the first version that supports structured outputs" (structured outputs), so AZURE_OPENAI_API_VERSION must name one that does:

using JSON
schema = Dict("type" => "object", "additionalProperties" => false, "required" => ["name", "year"],
              "properties" => Dict("name" => Dict("type" => "string"), "year" => Dict("type" => "integer")))
chat = Chat(service=AZUREServiceEndpoint,
            response_format=UniLM.json_schema("person", "A person", schema; strict=true))
push!(chat, Message(Val(:system), "You extract facts."))
push!(chat, Message(Val(:user), "Extract the person: Ada Lovelace, born 1815."))
JSON.parse(text(chatrequest!(chat)))

The formats every provider shares are on Structured Output.

Reasoning

A Chat's reasoning_effort goes out as it is set; Azure's values "vary by model and include none, minimal, low, medium, high, xhigh, and max. Defaults vary by model as well", and "max works only with GPT-6 or GPT-5.6 models and the Responses API" (reasoning models), which this endpoint does not speak. The field needs an api-version from 2024-12-01-preview on (Setup). Cap a reasoning model's output with max_completion_tokens: "Reasoning models will only work with the max_completion_tokens parameter when using the Chat Completions API", and the cap covers "reasoning tokens, visible output tokens, and formatting tokens". On this endpoint max_tokens keeps its name, so a request to a reasoning model sets max_completion_tokens instead. "Reasoning tokens are billed as output tokens": they count in completion_tokens, reasoning_tokens among them, and Chat Completions returns no reasoning text, so reasoning_text gives nothing.

chat = Chat(service=AZUREServiceEndpoint, reasoning_effort="low", max_completion_tokens=2000)

Attachments

A user message's attachments go out as content parts: an image as an image_url part, with its detail when one is set, a sound clip as an input_audio part, and a document as a file part holding its name and a data URL; the deployment's model decides what it reads, and UniLM checks none of it before sending. The attachments every provider shares are on Attachments.

Limits and refusals

A deployment's quota sets its tokens and requests per minute (quotas and limits), and a request past them meets HTTP 429 (When something fails). UniLM checks no limit of Azure's, and none of the per-model rules it applies on its native endpoint for the GPT models: every field a Chat sets goes out as it is — max_tokens keeps its name, user is sent, service_tier and reasoning_effort are not checked — and Azure's answer is the check. It refuses nothing of Azure's own before sending, only the checks every Chat gets, such as a temperature from 0 to 2 or an n of 1; the verbs of the capabilities the table at the top of this page lists as not available refuse the endpoint.

Prompt caching

Azure caches the prompts of the models that support it on its own: "cache reads are billed at a discount on input token pricing for Standard deployment types and up to 100% discount on input tokens for Provisioned deployment types" (prompt caching). The reply's prompt_tokens_details.cached_tokens becomes usage.cached_tokens, billed at the cached rate (Cost and usage). The cache fields go out as they are set, and Azure answers them:

  • prompt_cache_key: on the GPT-5.6 models and later, "reuse the same key for requests that share long, common prompt prefixes".
  • prompt_cache_options: its ttl "30m value is the default and the only supported value", and "Models before the GPT-5.6 family don't support prompt_cache_options or prompt_cache_breakpoint. Requests that include these parameters return a 400 error".
  • prompt_cache_retention: in_memory or 24h on the models before GPT-5.6, where it "selects a maximum-retention policy".

Cost and usage

estimated_cost prices an Azure result at the model's row of DEFAULT_PRICING, looked up by the model Azure reports, without its dated suffix, else the model the Chat names; the rows hold OpenAI's list prices, and Azure's own are not in UniLM. It bills the standard rates: input, cache reads at the cached rate, output, and a reported cache write at the input rate. No service-tier, long-context or cache-write multiple applies to an Azure result, though Azure bills GPT-6 and GPT-5.6 models in "separate pricing categories for short-context and long-context requests" (models). A model without a row is estimated at 0.0, with one warning per model id, and a result whose usage counts audio tokens at 0.0, with one warning per model and endpoint, since a row holds no audio rates. cumulative_cost adds up a Chat's turns; how a call is priced on every provider is on Cost Tracking.

When something fails

chatrequest! returns what Azure or the network did as a typed result, and does not throw it (Results). A failure holds Azure's HTTP status and, as response, the body that came with it; a call error holds the text of an exception as error and the exception as cause. UniLM sends a request again after a transient status — 408, 429, 500, 502 to 504, 520 to 524 and 529 — or a failed connection, as often as the call's RequestConfig allows, and then returns the last answer (Timeouts & Retries); a streamed request is sent again only while none of its callbacks has run.

Models

A Chat names a model id, and the model's deployment serves it (Setup). Azure's catalog lists the GPT-6.1, GPT-6, GPT-5.6, GPT-5.5, GPT-5.4 and GPT-5.2 series among others (models).

chat = Chat(service=AZUREServiceEndpoint, model="gpt-6-luna")   # AZURE_OPENAI_DEPLOY_NAME_GPT_6_LUNA

The v1 API

Azure's v1 API "removes the need for dated api-version parameters"; its base URL is the resource with /openai/v1 appended, and a request names the deployment as its model (v1 API). AZUREServiceEndpoint does not speak it. A GenericOpenAIEndpoint whose base URL is the resource's /openai path sends POST …/openai/v1/chat/completions, with the key as Authorization: Bearer:

v1 = GenericOpenAIEndpoint("https://your-resource.openai.azure.com/openai", "", "AZURE_OPENAI_API_KEY")
chat = Chat(service=v1, model="your-gpt52-deployment")

Azure's REST example of the v1 API sends a key in an api-key header and a Microsoft Entra ID token as Authorization: Bearer; a key sent as Authorization: Bearer, as here, is untested, and so is this route. Through it, a request has the generic endpoint's rules: no default model and no deployment lookup, the Chat's model sent as the deployment's name and the reply priced by the model Azure reports, and the capabilities of a generic endpoint, sent unchecked (OpenAI-compatible services).

Checked against Azure OpenAI's documentation of 25 October 2026 — the dated API version 2024-10-21 and the v1 API — with UniLM's development branch after 0.26.0; nothing on this page was run.
